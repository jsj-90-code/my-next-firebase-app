# 데이터/산식 불명확 항목 (점포평가 원본 분석)

> `reference/점포평가_V62_원본.xlsx` 전수 분석 중 발견된, 임의로 추측해서 채우지 않고 남겨둔 항목들이다. 각 항목에 확인한 시트/셀 근거를 남긴다.

## 2026-08-20 갱신 (5차) — 외부유입 보정 실제 반영 + 경쟁데이터 신뢰도·데이터완성도·운영상태·오차원인 추정 추가

- **실제 버그 발견 및 수정 — V62(외부유입 보정)가 검증화면에서 죽은 코드였다**: `validation/page.tsx`에
  `v62Rows`라는 변수가 있었지만 어디에도 렌더링되지 않았고, 화면에 나오는 MAPE/중앙값/±10%/±20%는
  전부 외부유입 보정 전 V61 값 그대로였다(주석에 "외부유입 값은 이 화면에서 별도 페치하지 않으므로
  '없음' 취급"이라고 스스로 적어놓고 방치돼 있었다). `runCohortValidation`이 이제 store별
  `inflowRestriction`(09_입지동선평가!외부유입제한)을 실제로 받아 V62 = V61×(1+보정률)을 계산하고,
  오차·방향·오차구간·목표달성 여부가 전부 이 V62 기준으로 바뀌었다. 그 결과 실제 라이브 데이터에서
  정식검증(26곳) ±10% 적중률이 정확히 57.7%로 나와 사용자가 전달한 06_검증대시보드 참고치와
  일치했다 — 보정을 실제로 적용하니 원본 시트 결과에 더 가까워졌다는 뜻이다.
- **또 다른 버그 — 조기검증에 브랜드 미확인 매장이 섞여 있었다**: `earlyNormalRows` 필터가
  `r.brand === "블랙라벨" || r.brand == null`이라 미확인 매장까지 조기검증 표본에 들어가고 있었다.
  `|| r.brand == null` 제거 — 이제 조기검증도 블랙라벨 확인된 매장만 들어간다(요청사항 1).
- **목표 수치 정리**: 화면에 별도로 하드코딩돼 있던 `ACCURACY_TARGETS`(10%/8%/80%/10%초과)를
  없애고, 이미 있던 `ModelSettings`(targetMAE 15%·targetMedianAE 10%·target20pctRatio 75%·
  maxAvgBias 5%)를 단일 출처로 쓰도록 통일했다. 여기에 없던 "±10% 이내 80%"를
  `target10pctRatio`로 새로 추가했다(정식 도입의 핵심 조건, 요청사항 8).
- **경쟁점 조사상태·데이터 신뢰도**(`computeCompetitorInvestigationSummary`), **데이터완성도
  25점×4항목**(`computeDataCompleteness`), **운영상태 enum**(`computeOperationalStatus`),
  **오차원인 우선 추정**(`classifyErrorCause`, 8종 — 단일 확정 진단이 아니라 화면에 "우선 추정
  원인"으로만 표시)을 새로 만들어 검증화면에 반영했다(요청사항 4/5/6/7).
- **parity test**: `06_검증대시보드` 참고치(정식검증 26곳 11.7%/9.1%/57.7%/76.9%, 조기검증 5곳
  13.8%/13.4%/20.0%/80.0%)를 실측 데이터(정식검증은 기존 골든데이터 VALIDATION_ROWS, 조기검증은
  사용자가 전달한 5개 매장 실제 절대오차율)로 fixture화해 `summarizeValidationRows`가 그대로
  재현하는지 테스트했다(calc.test.ts). 정식검증/조기검증 26+5=31곳은 이미 실측값이 있어 이렇게
  검증했지만, "통합(31곳)" 집계치는 시트에 매장별 분해가 없어 별도 fixture 없이 화면에서
  참고 비교만 한다(지어내지 않음).
- **정직하게 보고할 결과**: 위 버그를 고치고 나니 라이브 데이터 기준 정식검증(26곳)의 현재 상태는
  ±20% 적중률(73.1% < 목표 75%)이 근소하게 미달해 **"재보정 필요"**로 나온다(전엔 이 지표가
  실제로 반영이 안 됐으니 몰랐던 결과다). MAPE 12.1%·중앙값 8.8%·±10% 57.7%는 각각 목표(15%/
  10%/80%) 중 ±10%만 못 채운다. ±20%가 근소하게 걸리는 매장 하나(구미산동점 등 상권규모 과대추정
  계통 오차, §10_오차원인분석 기록)를 개선하면 "조건부 사용"으로 넘어갈 여지가 있다.
- **매출DB 자동 신규매장 등록**: `scripts/syncSalesFromRevenueSheet.mjs`가 매출DB!E열(가맹해지여부)
  이 "정상"인데 아직 `storeEvalExistingStores`에 없는 매장을 자동으로 skeleton 등록하도록 확장했다
  (브랜드·요금 등은 09/01 시트에 없어 null로 남고, `migrateFullExistingStoreProfiles.mjs`가 있으면
  채운다). 첫 실행에서 92곳이 새로 등록됐다 — 대부분 오래전에 오픈했지만 09_입지동선평가에는
  없던 기존 매장들이라 즉시 학습표본이 되지는 않지만, 브랜드를 확인해 채우면 V61 학습표본을
  34곳보다 크게 늘릴 잠재 후보군이다.

## 2026-08-20 갱신 (3차) — 브랜드 미확인 11곳 해소 + 특수수요 4번째 피처 실험(반영 안 함)

- **(2) 브랜드 미확인 11곳 + 동탄북광장점 해소**: 사용자가 09_입지동선평가에 이 12곳(발산역점·
  야당점·강릉교동점(신)·일산탄현점·장산점·평내호평점·진주혁신도시본점·문산점·인천서창점·송도점·
  동탄북광장점·N003호구포역점 등, 시트는 41→42행)의 상권 판단 데이터를 추가로 채워 넣었다
  (`scripts/migrateFullExistingStoreProfiles.mjs` 재실행으로 Firestore 반영 완료). 전부 브랜드구분
  "블랙라벨"로 확인됐다. 다만 V61 학습 표본 수는 여전히 34곳 그대로다 — 이 신규 확인분은 대부분
  12개월 미완료·오픈 초기 매장(위 §12개월 미완료 코호트 대상)이라 `isEligibleForV61Training`의
  실제매출 조건을 아직 못 채운다. 브랜드 확인 자체는 코호트 검증표(재직기간군 분류)에는 즉시
  반영된다.
- **특수수요(대학가/군부대/산업단지) 점수를 V61 4번째 학습 피처로 추가하는 실험 — 반영하지
  않기로 결정**: `computeSpecialDemandScore`를 만들어 34개 학습표본(위 브랜드 확인분 추가 후
  재확인해도 특수수요 태그가 있는 표본은 8곳 그대로 — 나머지는 태그는 있어도 학습 표본 자격이
  없음)에 대해 리브-원-아웃으로 3피처 대비 4피처를 비교했다.
  - 3피처(현재 프로덕션): MAPE 13.85%, 중앙값 9.99%, ±10% 52.9%, ±20% 79.4%
  - 4피처(특수수요 포함): MAPE 13.74%, 중앙값 10.25%, ±10% 50.0%, ±20% 76.5%
  - MAPE는 소폭 개선되지만 중앙값·±10%·±20% 세 지표가 전부 악화돼 방향이 일관되지 않는다.
    개별로도 금촌역·전대후문·울산대·시흥정왕·탕정역은 개선, 전대상대·청주대·부경대는 악화로
    나뉘어 "특수수요=항상 과소예측 보정"이라는 가설이 표본 8개로는 안정적으로 성립하지 않는다.
  - 표본 34개에 피처를 하나 더 늘리는 것 자체가 과적합 위험을 키운다는 점도 고려해 **프로덕션에는
    반영하지 않고 3피처 모형을 유지**한다. 흥미롭게도 원본 스프레드시트의 `11_보정안검증` 시트에도
    "특수수요 가산" 보정안이 과거에 시도됐다가 탈락 처리된 기록이 있어(§10 참고), 이번 실험 결과와
    같은 방향이다.
  - `computeSpecialDemandScore`/`V61TrainingStore.specialDemandScore`/09_입지동선평가 K·L열 마이그레
    이션은 코드에 남겨뒀다 — 학습표본이 지금보다 늘고(특히 특수수요 태그가 있는 매장이 8곳보다
    많아지고) 나면 재실험할 수 있게 하기 위함이며, 현재는 예측 계산에 쓰이지 않는다(진단/향후
    재실험용 필드).

## 2026-08-20 갱신 — `점포평가.gs`/`repair.gs` 원본 코드 확보

사용자가 Google Apps Script 편집기에서 `점포평가.gs`(V61)와 `repair.gs`(V04, 진단용 유틸)
전체를 채팅으로 붙여넣어 확보했다(로컬 사본: `reference/apps-script/`, gitignore 처리됨).
이로써 아래 항목들이 **웹 구현에 실제로 반영되었다** — 각 항목의 세부 근거/한계는 그대로
남겨두고 상태만 갱신한다.

- **#1 (V61 알고리즘)**: 부분 해결. "비음수 릿지회귀 60%+대당월매출 중앙값 40%" 알고리즘 자체는
  `fitNonnegativeRidge_`/`fitEmpiricalRevenueModel_`/`predictEmpiricalRevenue_`로 정확히
  확인되어 `src/lib/storeEval/calc.ts`에 그대로 포팅했다(`fitNonnegativeRidgeRegression`/
  `fitEmpiricalRevenueModel`/`predictEmpiricalRevenue`, 골든 테스트는 없지만 합성 데이터로
  단위 테스트함). **다만 학습에 필요한 기존 가맹점 특징 데이터**(12개월 완료·정상영업·
  산식학습제외 아닌 표본마다 자사_요금표_시간당·예측_자사수요/PC·자사_경쟁력점수를 계산해 둔
  값)가 아직 앱/Firestore에 없다 — README.md §4에 이미 나와 있듯 기존 가맹점 매출DB 연동
  자체가 자동화되지 않은 상태라, 이 세 특징치를 모을 파이프라인이 먼저 필요하다. 그때까지
  `evaluate.ts`는 계속 `computeV61Fallback`(13_신규후보지판정!G열 폴백 회귀식)을 쓴다.
- **#5 (40개 상권 평균 연령구성)**: 완전 해결. `CONFIG.MARKET.기본연령구성`/`기본남성비율`에
  정확한 수치(10대7%·20대9%·30대14%·40대20%·50대23%·60대이상27%, 남성비율55%)가 있었다.
  `computeFloatingRawDemand`가 이제 이 값으로 폴백해 유동인구 평균만 있어도 원수요를 계산한다
  (더 이상 null을 반환하지 않는다). 단, 주거(1km) 원수요는 원본에도 폴백이 없어(연령 미입력 시
  `residentDemand_`가 null 반환) `computeResidentRawDemand`는 기존 그대로 유지한다.
- **#7 (사양/좌석/입지 점수)**: 완전 해결. `scoreFromVga_`/`scoreFromSpecWithMonitor_`/
  `scoreFromZoneComposition_`/`scoreFromAccess_`의 정확한 변환표를 확보해 `calc.ts`의
  `computeSpecScore`/`computeSeatScore`/`computeLocationScoreFromFacts`로 그대로 포팅했다.
  더 이상 1~5점 직접 입력이 아니라 VGA 모델명·존 개수·층수+엘리베이터로부터 자동 계산되며,
  화면(BasicInfoTab/CompetitorsTab)도 입력란을 읽기전용 자동계산 표시로 바꿨다. 이 과정에서
  독립룸수 계산식이 종전엔 "팀룸×2+커플존×3+VIP존×5"(추측해 만든 가중치)였는데, 원본은
  가중치 없이 **개수를 단순 합산**(`summarizeZones_`)한다는 게 확인되어 바로잡았다
  (`computeZoneComposition`).
