## 2026-08-30 갱신(당일 마지막) — 블랙라벨 41곳 입지동선평가 AI 일괄 재실행 + competitorIp 품질가중 검토 기각 + 검증화면 오차구간 시각화

- **입지동선평가 AI 일괄 재실행**: 사용자가 청주지웰시티점 하나를 수동으로 "AI로 초안 채우기"
  다시 돌려보니 값이 달라진 것을 계기로, 블랙라벨 41곳(리그PC방/확인필요 92곳은 제외 — 사용자
  명시) 전체에 대해 사람 검토 없이 AI 초안을 자동 적용+저장했다(임시 스크립트로 실행, 코드
  변경 아님 — 스크립트는 작업 후 삭제함). 기존 저장된 경쟁점/수요거점/행정동통계는 재사용하고
  없는 1곳(검단사거리점)만 카카오/SGIS 즉석 재조회. Gemini 503(모델 혼잡)로 실패한 건은 최대
  2회 재시도해 **최종 41/41 전부 성공**.
- **⚠️ 방향성 있는 변화 확인(무작위 노이즈 아님)** — 39곳 before/after 비교 결과:
  - 상권내위치점수: 24곳 하락 / 2곳 상승 / 13곳 동일
  - 주요동선점수: 27곳 하락 / 1곳 상승 / 11곳 동일
  - 접근가시성점수: 17곳 하락 / 2곳 상승 / 20곳 동일
  - 상권흡인력점수: 23곳 하락 / 1곳 상승 / 15곳 동일
  - 선점경쟁점수: 22곳 **상승** / 3곳 하락 / 14곳 동일 (유일하게 반대 방향)
  - 즉, 최신 Gemini 평가는 예전보다 위치/동선/가시성/흡인력은 더 박하게, 선점경쟁(경쟁점이
    좋은 자리를 선점해서 불리한 정도)은 더 후하게 보는 경향이 뚜렷하다. `computeLocationCompositeScore`
    가중치(위치30%+동선30%+선점경쟁25%+가시성15%)로 보면 하락 요인 3개(위치·동선·가시성,
    합 75%)가 상승 요인 1개(선점경쟁 25%)보다 크므로, **자사 경쟁력점수의 입지10% 컴포넌트가
    전반적으로 낮아질 가능성이 높다** — V61 예측매출이 전반적으로 소폭 낮아지는 방향으로
    움직일 수 있다는 뜻이다. 좋다/나쁘다 판단은 아직 이르고, 다음 크론 이후 검증화면 적중률
    변화로 확인해야 한다.
  - mapMemo에는 기존 메모를 지우지 않고 "AI 초안(일괄재실행): ..." 근거를 이어붙였다(원래
    화면의 개별 적용 로직과 동일한 append 방식).
- **아직 competitivenessScore 캐시에 미반영** — cronSync가 `storeEvalLocationEvaluations`를
  읽어 competitivenessScore를 재계산하는 건 **다음 정기 동기화(매일 06:00 KST cron)**가
  돌아야 실제로 반영된다. 이번 세션에선 배포 도메인을 확인 못 해 수동 트리거를 안 했다 —
  **내일 작업 시작하면 제일 먼저 검증화면(±10%/±20%, 오차구간 막대그래프) 수치가 오늘 이전과
  달라졌는지부터 확인할 것.** 나빠졌다면 위 "방향성 있는 변화"가 원인일 가능성이 크다(수동
  보정 대신 원인부터 다시 진단할 것 — 역산 금지 원칙 그대로).
- **competitorIp 품질가중 아이디어 검토 → 기각**: 청주지웰시티점 질문("경쟁점이 존구성 아예
  없는데 왜 예상매출이 낮지?")에서 나온 가설 — `competitorIp`(경쟁점 PC대수 합, 품질 무관)를
  경쟁점 `competitivenessScore`로 가중해서 "경쟁점이 약하면 그만큼 자사가 더 먹는다"를 반영하면
  어떨지 검토했다. 정식검증 26곳 중 경쟁점 있는 23곳으로 실측: (raw competitorIp - 품질가중
  competitorIp)와 (실제매출-예측매출) 잔차의 상관계수 = **0.10**(n=23 유의하려면 대략 0.41
  이상 필요) — 이론상 그럴듯해도 실제 데이터에 뚜렷한 패턴이 없어 **채택하지 않음**. 참고로
  청주지웰시티점 저평가의 실제 원인은 이미 확인된 대로 자사 존구성 편중(§경쟁력 평가 기준
  최종본의 좌석·존구성 다양성 가산 방식) — 경쟁점 약함과는 별개다.
- **검증화면(`/store-eval/validation`) 오차구간 막대그래프 추가**: 10%p 단위 오차구간
  분포(`summarizeValidationRows`의 `buckets`, 기존에도 계산은 있었으나 "자세히 보기(전문가용)"
  안에 텍스트 표로만 있어 눈에 안 띄었음)를 헤드라인 배너 바로 아래, 접히지 않는 위치에
  막대그래프로 새로 추가(`ErrorBucketChart`, `validation/page.tsx`). 새 계산 없음 — 기존 결과를
  보여주는 방식만 바꿈. 정식+조기검증 통합(combinedSummary) 기준.

## 2026-08-30 갱신 — 경쟁점 초과수요를 자사로 재배분(가동률 상한의 대칭 확장)

바로 위 가동률 상한 건에 이어 사용자가 문제제기: "경쟁점도 수요를 초과하는 경우가 있을 텐데,
그럼 그 초과분은 자사가 더 가져가야 하는 거 아니야?" 처음엔 "방문객 수(명) ↔ 가동률" 사이의
환산계수가 없어 보류했는데, 사용자가 실측치(고객 1명 월평균 방문 3.7회, 1회 이용시간 3시간)를
줘서 계산 가능해졌다.

- **환산**: PC 1대당 월 최대 고객수 = `24시간×30일×가동률상한(0.55) ÷ 이용시간(3) ÷ 월평균방문(3.7)
  ≈ 35.68명`(`computeMaxCustomersPerPc`).
- **신설**: `redistributeCapacityConstrainedDemand` — 경쟁점별로 "PC대수×경쟁력점수"(pull)에 비례해
  상권수요를 먼저 나눠보고, 개별 경쟁점의 배정량이 자기 물리적 상한(대수×35.68명)을 넘으면 초과분을
  자사로 넘긴다. 자사도 같은 상한으로 클램프한다(사용자 확인: "대신 우리도 상한이 있겠지만"). 초과
  고객수는 `computeCapacityOverflowRevenueBonus`로 매출 환산(방문횟수×이용시간×요금÷(1-상품비율))해
  V62Final에 더한 뒤, 기존 `applyCapacityCeiling`으로 자사 상한을 한 번 더 확인한다(이중 안전장치).
- **적용 범위**: 후보지 평가(`evaluate.ts`)에만 적용, `runCohortValidation`(LOOCV 백테스트)에는 적용
  안 함 — 아래 실측 확인대로 26곳 전부 이 재배분이 0(경쟁점이 상한을 넘는 사례가 실측 데이터에
  하나도 없음)이라 백테스트에 반영해도 검증할 근거가 없고, 시그니처만 복잡해질 뿐이라 범위에서 뺐다.
- **실측 확인(별도 조사 스크립트)**: 정식검증 26곳 전부 재배분 보너스 = 0원 — 이 기능이 실제
  적중률을 개선하는지 악화시키는지 지금 데이터로는 검증할 수 없다(안전하지도, 위험하지도 않고
  그냥 지금은 발동을 안 함). 로직 자체는 이미 승인된 자사 상한과 대칭 구조라 위험은 낮다고 판단,
  기본 켜둔 채로 배포한다 — 향후 경쟁점이 실제로 상한을 넘는 후보지가 나오면 그때 결과를 지켜볼 것.
- 새 설정값 `customerVisitsPerMonth`(3.7)/`customerSessionHours`(3)/`v62MaxUtilizationRate`(0.55,
  위 항목과 공유)는 전부 `settings.ts`에 하드코딩 대신 ModelSettings로 관리한다(원칙 준수).

## 2026-08-30 갱신 — V61/V62 예측매출에 물리적 가동률 상한(55%) 신설

사용자 문제제기: "가동률이 물리적으로 100%를 넘을 수 없고, 24시간 평균으로 60~70%도 비현실적인데
(그러려면 새벽에도 거의 만석이어야 함), V61/V62엔 이걸 걸러줄 상한이 없다." 실제로 확인해보니
과거 어떤 후보지에서 예상 평균가동좌석이 계획 PC대수를 넘어 가동률 125.9%가 나온 사례가 이미
있었고(2026-08-21 기록), 이건 "실측기반 예상월매출"(AA경로, 이미 미검증 참고지표로 격하됨) 얘기였을
뿐 핵심 V61/V62 예측 자체엔 아무 물리적 제약이 없었다.

- **실측 검증**: 정식검증 26곳의 실제매출을 `computeImpliedUtilizationFromRevenue`로 역산해보니
  전부 20.2%~48.7%(24시간 평균) 범위였다 — 60~70%는커녕 50%를 넘는 매장이 단 하나도 없었다.
  사용자 직관이 데이터로 뒷받침됨.
- **신설**: `applyCapacityCeiling`(calc.ts) — 예측매출을 상한이 함의하는 가동률로 환산했을 때
  넘으면, 정확히 상한 가동률에 해당하는 매출로 깎는다(`computeMeasuredForecast`와 같은 공식의
  정방향 재사용, 새 계수 없음). 상한값은 `settings.v62MaxUtilizationRate`(기본 **0.55** — 최대
  관측치 48.7%에 여유를 조금 둔 값, 사용자 확정).
- **적용 범위(사용자 확인)**: 후보지 평가(`evaluate.ts` v62Final)와 검증화면 LOOCV 백테스트
  (`runCohortValidation`) 둘 다에 일관 적용. **실측 확인: 26곳 백테스트엔 영향 0**(현재 예측이
  전부 상한 밑이라 아무것도 안 깎임) — 극단적으로 외삽된 신규 후보지 예측에만 실제로 작동한다.
- **"넘친 수요는 경쟁점 몫" 해석**: 별도로 경쟁점 매출 숫자를 계산하지 않는다(이 앱은 애초에
  경쟁점 매출을 예측 대상으로 안 삼음) — 자사 예측을 물리적으로 타당한 값으로 제한하는 것 자체가
  "그 초과분은 자사가 못 가져간다"는 의미를 이미 담고 있다고 판단. `expectedOwnDemand`(방문객
  수요, 단위=명)에는 캡을 안 씌웠다 — 가동률(좌석 점유율)과 방문객 수는 단위가 달라
  (인당 방문횟수·체류시간 변환계수가 필요한데 근거 없음) 억지로 엮으면 새 가정을 지어내는 셈이라 보류.
- **금지원칙과의 관계**: "적중률 위해 계수 역산 금지"와는 성격이 다르다고 판단(사용자 확인) —
  실측값에 맞추려는 보정이 아니라 PC 대수로 물리적으로 낼 수 없는 값을 거르는 제약이라서다.
- UI: 상한에 걸리면 결과화면(ResultTab)·리포트카드(ReportCard)에 "가동률 물리적 상한 적용됨 —
  원래 예측 X원" 경고를 표시한다(값을 조용히 안 바꾸고 항상 원래값도 같이 보여줌).

## 2026-08-30 갱신 — 최종본 적용 후 적중률 원인분리 + 인테리어 비중 재조정 + 먹거리 표준값 정정

최종본 적용 직후 정식검증 26곳 적중률이 57.7%→46.2%(±10%)로 떨어진 걸 발견해 원인을 6개 요인으로
쪼개 하나씩 되돌려보며 확인했다(전부 "그날 수정된 현재 데이터" 고정, 산식만 교체 — 재구성값이
실제 배포값과 정확히 일치함을 확인 후 진행).

- **최신성점수 자동계산(§7)이 압도적 1위 원인**: 이전엔 26곳 전부 최신성 항목이 공란이라 인테리어
  점수가 사실상 4점 고정값이었는데, 오픈연도로 자동 채워지면서 매장마다 2.5~5.0점으로 벌어졌다.
  26개뿐인 학습표본의 릿지회귀 피팅이 이 새 신호에 흔들린 것 — 2026-08-20 특수수요 4번째 피처
  추가 후 롤백했던 것과 정확히 같은 패턴(표본이 적을 때 새 신호 주입=과적합 위험).
  이 요인만 되돌리면(직접입력만 사용) 46.2%→53.8% 회복.
- **먹거리 브랜드/우선순위 변경**: 영향 0. 26곳 전부 브랜드 미지정이라 먹거리점수가 전 매장 동일한
  표준값이고, 릿지회귀 z-score 표준화가 상수를 완전히 상쇄한다 — 브랜드 값을 아무리 조정해도 이
  26곳 백테스트엔 무관(신규 후보지 평가엔 정상 반영됨, 별개).
- **09_입지동선평가 입지점수 통합(§12)**: 오히려 개선 요인 — 되돌리면(층수+엘리베이터만) 42.3%로
  더 나빠진다. 41곳이 실제로 폴백과 다른 값을 받고 있어 유의미하게 기여 중.
- **좌석·존구성 자동계산**: ±10%엔 영향 없지만 ±20%/MAPE는 오히려 악화(다른 요인과 비선형 상호작용).
- **하드웨어표·반올림 제거**: 각각 3.8p 정도씩 소폭 기여.
- **경쟁점 여러 개일 때 수요점유율 공식 재검증(사용자 문의)**: `경쟁력격차=자사점수÷경쟁점_PC대수
  가중평균점수`를 쓰기 때문에, 대수식을 정리하면 `자사점수×자사대수 ÷ (자사점수×자사대수 +
  Σ(경쟁점_i점수×경쟁점_i대수))`로 완전히 같아진다는 걸 확인했다(경쟁점이 몇 개든 개별 가중
  합산과 수학적으로 동일) — 실측(4점 1개 vs 4점+2점 2개, 동일대수 가정)으로도 확인: 50%→40%로
  정상적으로 감소, 반직관적 사례 없음. **버그 아님, 조치 불필요.**
