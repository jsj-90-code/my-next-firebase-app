# 경쟁점 가동률 측정기 (`/ping-monitor`, 2026-10-06 신설)

옛 핑봇(`ping.isens.camp`)은 유지보수가 끊겼다. 사용자가 직접 쓰려고 새로 만들었다 — 경쟁점 **상호·주소·IP대역**만 넣으면
1시간마다 켜진 PC를 세어 가동률을 **기한 없이** 쌓는다.

## 어떻게 재나

- Vercel 함수는 핑(ICMP)을 못 보낸다. 대신 IP마다 포트 두 개(80·3389)에 **TCP 연결을 한 번 시도**한다.
  켜진 PC는 "연결 거절"을 바로 돌려주고(=켜짐), 꺼진 PC는 대답이 없다(=꺼짐). 문을 여는 시도가 아니고, 포트 스캔도 아니다.
- 2026-10-06 실측: `118.128.168.1~110`에서 핑과 TCP 결과가 110개 전부 일치(11:10 5대, 11:50 6대).
- `115.89.100.1~140`(옛 핑봇도 못 재던 곳)은 핑·TCP 모두 0/140, 공유기(254)만 대답 → **PC가 바깥 확인을 막아 둔 매장**.
  이런 곳은 72번 넘게 재도 0이면 화면에 "측정 불가 의심"으로 따로 뜬다(가동률 0%로 섞지 않으려고). 기준값은 `summary.ts`의 `BLOCKED_SUSPECT_SAMPLES`.
- Windows에서 시험할 땐 거절이 ~2.1초 늦게 온다(재시도) — 대기 시간이 Windows 4초·서버 2초인 이유.

## ⚠️ 등록된 IP대역 안에만 보낸다 (사용자 규칙 2026-10-06)

핑·TCP는 **등록된 IP대역 안의 주소에만** 보낸다. 같은 /24의 범위 밖 주소는 공유기·다른 기기·**다른 사업장**일 수 있다.
같은 날 IP 점검에서 /24 전체를 훑은 적이 있는데(범위 오류 추정 12곳의 근거) 이 규칙에 어긋나 다시 하지 않는다 — 그 12곳은 추정으로만 두고 현장 확인으로 고친다.
"장비가 대신 대답" 판단도 범위 안 결과만으로 한다.

## ⚠️ TCP만으론 일부 매장을 못 본다 (2026-10-06 13시대 106곳 실측)

서버가 TCP로 잰 직후 사무실 PC에서 핑으로 다시 쟀다: 둘 다 대답 33 · **핑에만 23**(이로운 94·아이비스 91·티티 36 등 — TCP로는 0) ·
TCP에만 15(제스트 46·PC토랑 40 등) · 둘 다 0 35. PC방마다 막아 둔 방식이 달라 **핑 또는 TCP 하나라도 대답하면 켜짐**이 맞다.
핑은 Vercel·GitHub에서 못 보내서 진짜 서버(Oracle 무료, 일본 도쿄 — 서울·춘천은 가입 목록에 없었음)가 필요한데,
같은 날 오후 사용자가 가입했다 → **2026-10-06 17시 기록부터 Oracle 서버가 핑 + TCP를 합쳐 잰다**(방식이 바뀐 시각).
그 전(13~16시) 기록은 Vercel TCP만이다 — 지난 기록은 그대로 둔다. 시간별 기록의 `m` 칸에 잰 방식이 남는다(`icmp+tcp` / `tcp`).
첫 실측(17시): 매장 239 · IP 22,864 · 켜짐 6,016(핑만 834 · TCP만 1,907) · 약 10분. 서버 안내: `scripts/pingMonitor/agent/README.md`.

## ⚠️ 장비가 대신 대답하는 곳 (2026-10-06 16시 점검)

등록 IP 거의 전부가 대답하는 곳이 있다 — PC가 아니라 공유기·방화벽이 대신 대답해 가동률이 부풀려진다.
TCP: PC토랑 135/135 · 플레이존 386/400. 핑: 아이비스 90/100 · 보보스1 · EFC · 엔피시 · 라이또PC(85% 이상). 사용자가 예전에 "이로운 78.9% 가짜"라고 한 것도 같은 현상.
범위 안 결과만으로 판단해 웹에 **"IP 확인 필요"**로 표시했다(`ipCheck`, 51곳 — 범위 안 0대 43 · 대신 대답 의심 7 · 추정 범위 1). 사용자가 직접 찾아 고친다. IP를 고쳐 저장하면 표시가 지워진다.

## 시트 보류 15곳 정리 (2026-10-06 오후)

- 사용자: 시트의 새 탭을 예전 탭에서 복사해 만들고 안 지운 칸이 있다 → **매장끼리 같은 IP는 복사 잔재**.
  - 금촌역 탭의 데일리·에스알피 = 동탄 것(옛 핑봇 "동탄북광장점"으로 이미 등록). 야당 탭 레벨업 IP(211.168.194) = 금촌 3pop(옛 핑봇 "3pop pc 금촌").
    야당 레벨업 진짜 IP는 210.206.98.1~183(옛 핑봇).
  - 부천상동 클리드 ↔ 부경대 O.X(210.220.120): 실측 TCP 42대가 .13~.129에 퍼져 88대 O.X가 아님 → **클리드 1~149 등록**.
- 끝자리 255 초과 4곳(포텐·오토피씨·플레이존·브리즈)과 셀하는 다른 창이 옛 핑봇 IP로 이미 등록.
- 룸앤룸(구미산동) "217(87)" = 87번 자리가 .217 → 자리 n = .130+n 추정으로 **.131~249 등록**(그 구간 11대 대답, .1~81은 다른 매장으로 봄).
- TO PC(울산대): .1~244 전체가 대답해 매장 하나로 못 가림 → 보류.
- **대수 > 아는 IP 수인 7곳**(오토피씨 302/168 등)은 가동률이 눌려 나와서 대수를 비워 IP 수로 나누게 했다(모르는 IP의 PC도 같은 비율로 켜져 있다고 봄).

  상호·대수·거리가 자동으로 채워지고 `competitorId`로 이어진다.
- 목록 기본은 "매장별": 묶음 머리에 경쟁점 7일·30일 가동률(켜진 합 ÷ 대수 합), 누르면 펼쳐지며 경쟁점 표가 뜬다.
  옛 핑봇 값 칸은 처음엔 나란히 띄웠다가 2026-10-06 사용자 요청으로 뺐다("옛 핑봇 가동률은 몰라도 될 듯").

## 칸 나누기와 우리 매장 가동률 (2026-10-06 저녁)

- 목록은 **기존가맹점 / 신규후보지 / 경쟁점 전체** 세 칸. 후보지는 `ownCode`가 N0xx인 매장. 우리 매장에 안 이어진 경쟁점은 "경쟁점 전체"에만.

    울산삼산 피에스타는 3/101(오전 9시 반 측정) — 손님 많은 시간에 다시 재 볼 것.
  - 안 넣은 판단: 강릉 오셀롯←크레인(47m, 대수 81 vs 95), 울산삼산 욜로←레벌업(레벨업이 2m로 더 가까움).
- **KISA 후이즈(IP 할당 기관 조회)는 쓸 수 없다(2026-10-07 판정)** — 포트 43(`whois.kisa.or.kr`, 인증키 불필요)으로 IP를 아는 20곳을
  조회하니 **상호가 나온 곳 0/20**. 전부 통신사(KT·LG유플러스·SK브로드밴드)이고, 우리 매장 3곳조차 통신사로만 나온다.
  통신사가 소상공인 고객 이름을 등록하지 않기 때문 — 다시 시도하지 말 것. (조회는 KISA 서버에 묻는 것이라 매장 IP로는 아무것도 안 보낸다.)
- **방문 조사 양식 개선안(2026-10-07 제안 → 사용자: 양식은 안 바꾼다)** — 지금 양식은 `IP 주소 :` 한 칸이라 IP 하나만 적혀 온다(김포풍무 2곳 보류 이유).
  주변을 훑지 않기로 했으니 IP 하나로는 PC 한 대만 잴 수 있다. → "번호가 가장 앞인 자리·가장 뒤인 자리(가능하면 가운데 하나 더) PC에서
  브라우저로 '내 IP' 검색해 자리 번호와 같이 적기(한 대 10초)". 두 끝 IP 사이만 등록하고 precheck로 5대 이상인지 확인.
  세 대가 같은 IP면 공유기 매장 = 측정 불가로 적는다(헛걸음 방지). 자리 번호와 IP 끝자리가 이어진다고 가정하지 않는다(하안금당 레벨업 0/100).
- **바깥 경로 검토(2026-10-07, 사용자 질문: 통신사·게임사·노하드 업체에서 끌어올 수 있나)** — 셋 다 경쟁점 IP를 *갖고는* 있지만 공개 창구가 없다.
  통신사는 KISA 후이즈가 유일한 공개 창구(0/20). 게임사(라이엇·넥슨·크래프톤 등)는 PC방 가맹을 IP로 등록·과금하지만 목록은 내부 자료이고
  업주 본인만 자기 IP를 본다. 노하드·관리프로그램 업체(피카·게토 등)도 같다. 남의 매장 IP를 이들에게서 받는 건 고객 정보 제공이라 안 되고,
  게임사 가맹 조회에 IP를 넣어 보는 식은 결국 주변 IP 훑기라 규칙 위반. → **IP 대신 가동률 자체**를 주는 경로를 보는 게 낫다:
  피카플레이 앱(피카 관리프로그램 쓰는 약 6,300곳 PC방 찾기·예약)에 잔여 좌석이 보이는지 확인 필요, 게임트릭스류 지역 통계(집계값)는 제휴 문의 대상.

## 저장

- `pingMonitorStores/{id}` — 등록 정보 + `days.{YYYY-MM-DD} = {a: 켜진 수 합, t: 대수 합, n: 측정 횟수}` + `lastSample`.
  목록은 이것만 읽는다(매장당 읽기 1번).
- `pingMonitorDaily/{id}_{YYYY-MM-DD}.hours.{HH} = {a, t}` — 상세 화면 시간대별. 최근 92일까지만 읽는다(무료 요금제 읽기 한도).
- 가동률 = Σa ÷ Σt. 대수를 나중에 고쳐도 지난 기록 분모는 그때 값으로 남는다.
- 같은 한국 시(時)에 두 번 불려도 한 번만 센다(트랜잭션).
- 화면은 등록 칸만 쓸 수 있고 측정 기록은 서버만 쓴다. 지우기는 막았다(`firestore.rules`). 측정을 멈추려면 상세 화면에서 "1시간마다 측정"을 끈다.

## 알람 경위 (2026-10-06 하루 동안)

1. GitHub Actions + 비밀값(`PING_MONITOR_SECRET`) → 사용자가 비밀값을 손으로 넣어야 해서 막힘.
2. Vercel 예약 실행 매시(`vercel.json` crons) → **무료(Hobby) 요금제라 배포 거절**(커밋 35e205f, 예약은 하루 1번만 됨).
3. GitHub Actions + **OIDC 토큰**(지금) — GitHub가 서명한 신분증에 저장소·브랜치·이벤트가 들어 있어 서버가 직접 확인한다. 넣을 비밀값 없음.
   서버는 `CRON_SECRET`도 받으니, 요금제가 Pro로 바뀌면 `vercel.json`에 매시 예약을 넣고 워크플로를 지우면 된다.

## 옛 핑봇 값과 이어 쓰기
