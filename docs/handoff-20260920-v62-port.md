## 1. 무엇을 왜 적용하기로 했나 (판정 기준이 바뀌었다)

사용자(2026-09-19): *"v62라고 mape 위주로 진행하는 게 아니라, 근거가 명확한, 이런 값이라면

실험실에서 하루 종일 지킨 규율("MAPE로 값을 고르지 않는다")을 **운영에도 그대로** 적용한다.
그래서 근거를 **종류**로 나눈다:

```
  [사실 문제]  운영 값이 사실과 어긋난다        -> 적중률과 무관하게 고친다
  [통계 근거]  관문(위약·대조군·LOO)을 통과했다  -> 대가를 보고 정한다
  [판단]      뜻으로 고른 값이다              -> 사실 교정과 같이 넘기지 않는다
  [근거 약함]  실험실 안에서만 뜻이 있다        -> 안 건드린다
```

| 항목 | 종류 | 대가 | 상태 |
|---|---|---|---|
| 사양 **변환표**(GPU·CPU 성능지수) | 사실 | MAPE +0.05%p · ±10% 66→63% | ✅ **1단계 완료** |

| 사양 **비중** 0.4/0.25→0.5/0.15 | **판단** | — | ⛔ 안 함 |
| 사양 RAM·모니터 변환 | 판단 성격 | — | ⛔ 안 함 |

## 2. 1단계에서 실제로 한 일 (참고용)

`calc.ts`에 성능지수표를 **원본으로** 넣고 `scoreFromVga`/`scoreFromCpu`가 표를 먼저 보게 했다.
표에 없는 모델(AMD 라이젠 등)만 기존 세대 산술로 떨어진다.

```
  옛 식: 4 + (세대 − 5) + 티어보너스     <- 세대 숫자를 성능으로 읽었다
    RTX 3060 Ti 2.25 < RTX 4060 3.00   (실제로는 3060 Ti가 빠르다 · 23건)
    i3 13100F   3.00 = i5 13400F 3.00  (티어를 아예 안 본다 · 자사 9곳)
```

- 새 상수/함수: `GPU_PERF_INDEX` · `CPU_PERF_INDEX` · `scoreFromPerfIndex` ·
  `gpuPerfKey` · `cpuPerfKey` · `gpuGeneration` · `cpuPerfGeneration` + 눈금 상수들
- `calc.test.ts` 기대치 갱신 + **뒤집힌 서열을 잠그는 시험 2개 추가**
  (`3060Ti > 4060` · `3070 > 4060` · `4070 > 5060` · `i3 < i5 < i7`)

⚠️ `labSpecScore.ts`는 아직 자기 표(`LAB_GPU_PERF_INDEX` 등)를 들고 있다. **두 벌이 됐다.**

## 3. 2단계 — 존구성을 실험실 판으로

### 근거 (사실 문제)

경쟁점 조사표에 **VIP존·프렌즈존·퍼스트클래스존 칸이 228건 전부 0건**이다. 우리 브랜드
용어라 조사자가 경쟁점의 같은 실체(파티션 1인석 등)를 보고도 그 칸에 안 넣는다.
운영은 **존 이름 종류 수**로 다양성을 세니 **경쟁점이 아무리 좋아도 자사를 못 따라잡는다.**

실험실은 이름표를 **물리 좌석으로 환산**한다(사용자: *"자사의 VIP존은 1인석으로 바꼈고
프렌즈존은 2인석·3인석으로 변환했잖아"*):

```
  다양성 = **룸 종류 수만** (1인룸·2인룸·팀룸)   <- 양쪽 다 조사되는 물리 사실
  수용력 = **특화좌석 전부** (이름과 무관)
  비중   = 다양성 0.3 · 수용력 0.7
```

### 측정으로 확인된 것 (조사된 경쟁점 194곳 · 중앙값)

```
  [운영]   다양성 자사 3.50 / 경쟁 1.00  차이 2.50    수용력 3.00 / 1.00  차이 2.00
  [실험실] 다양성 자사 2.00 / 경쟁 1.00  차이 **1.00**  수용력 4.00 / 1.00  차이 3.00
```

**이름표 우위가 2.50 → 1.00으로 걷힌다.** 수용력 차이가 느는 건 VIP존이 1인석으로,
프렌즈존이 좌석으로 제대로 세어져서다 — 실재하는 좌석이라 맞는 방향이다.

⚠️ 총점은 3.35 → 3.40으로 비슷하다(둘이 상쇄). **승률로 보면 안 보이고 분해해야 보인다.**
   2026-09-19에 내가 승률만 보고 "안 고쳐진다"고 오판했다가 사용자 지적으로 철회했다.

### 할 일

1. `calc.ts`의 `computeOwnZoneComposition` / `computeCompetitorZoneComposition`을
   `labZoneComposition.ts`의 잣대로 바꾼다.
   - ⚠️ `labZoneComposition.ts`는 **calc를 import하지 않는다** → 순환 걱정 없다.
   - 자사엔 "일반 2인석" 칸이 없다(우리 2인석은 커플존으로 들어간다) — `own: true`로 구분.
   - 퍼스트클래스존은 **룸 1개 = 11석**으로 센다(사용자: 10~12석, 중간값).
2. 미조사 경쟁점 기본값(`UNSURVEYED_COMPETITOR_ZONE_SCORE` vs `LAB_UNSURVEYED_ZONE_SCORE`)이
   다른지 확인하고 하나로 맞춘다.
3. `calc.test.ts`의 존구성 기대치 갱신 + **이름표 비대칭이 줄었다는 시험 추가**

## 6. ⚠️ 2026-09-19에 내가 밟은 함정 넷 (같은 걸 또 하지 말 것)

1. **"후보지는 한 톨도 안 바뀐다"는 거짓이었다.** 칸을 더하면 나머지 계수가 다시 학습된다
   (공급 대비 수요 계수가 −29.6% 움직였다). 실제로 재니 최대 1.71%였다.
2. **상수 칸으로 후보지를 흉내내면 안 된다.** 전 매장에 같은 값을 넣으면 분산 0이라
   표준화에서 전부 0이 되고 학습이 기준선과 같아진다(변화 0.00%가 나왔다).
   올바른 흉내: **실제 값으로 학습 → 평균으로 예측.**
3. **승률로 편향을 판정하면 안 된다.** 존구성에서 자사 승률 98→100%만 보고 "안 고쳐진다"고
   오판했다. **다양성·수용력으로 분해해야** 이름표 우위가 걷힌 게 보인다.
4. **사실 교정과 판단을 섞어 재면 안 된다.** "사양 교체는 나빠진다"고 적었는데 비중 변경까지
   같이 넘겨서였다. 갈라내니 달랐다.

⚠️ 그리고 **숫자를 인용할 때 무엇까지 포함한 값인지 확인할 것.** "변환표만 9.06%"라고
   적었는데 그건 RAM·모니터까지 포함한 값이었고, 실제 GPU+CPU만은 9.22%였다.
