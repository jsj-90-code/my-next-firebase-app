### Codex 상호검토 — 내 보고서 오류 5건 수용 (2026-09-11 오후)

Codex가 `docs/claude-analysis-followup-20260911.md`로 내 검토보고서
(`releases/2026-09-11-claude-review-of-codex-audit.md`)의 계산 오류 5건을 지적했고
**전부 타당해 수용**했다. 정정은 그 보고서 맨 앞에 넣었다.

가장 무거운 두 가지:

1. **제안 1순위가 성립하지 않는다.** "총매출 수준은 안 건드리고 PC·먹거리 구성비만 상권별로
   조정"은 `P_new + F_new = (1-r)T + rT = T`라 **총매출 적중률이 정의상 안 바뀐다.**
   내가 "총액을 안 건드린다"고 써놓고 총매출 적중률 후보 1순위로 올렸다.
2. **목표 난이도 근거가 무효다.** 9.06%는 매장별 *평균절대편차의 중앙값*인데 이걸 표준편차처럼
   √11로 나눠 2.7%를 "표준오차"라 했고, 8.23%의 절반 ±4%를 "목표값 불확실성"으로 확정했다.
   그 위에 "±10% 80%는 구조적으로 어렵다"는 결론을 세웠다. **A-4(중간목표 65%)를 바꾸자는
   게 아니라, 이 보고서가 A-4의 근거가 되지 못한다는 뜻이다.**

나머지 셋 — 먹거리 가중은 "죽은 항"이 아니고(경쟁점 점수는 변하며 격차가 비율이라 자사
수준도 들어간다), 12×3 중 최대 상관을 단일 임계값과 대조한 유의성 주장은 철회하며,
42.96%는 "주관 인테리어"가 아니라 시설 종합(존구성 50%+인테리어 30%+관리 20%)이다.

**정정 결과 지금 바로 실행할 총매출 적중률 개선 후보는 남지 않았다.**

> **기록해둘 실수(반복)** — 관측된 숫자를 한 단계 더 밀어서 해석한다. MAD를 SD처럼,
> 최대 상관을 사전지정 상관처럼, 한 부분의 분산 0을 전체 무정보처럼. 수치를 인용할 때
> **그게 정확히 무엇의 통계량인지** 먼저 적는 걸로 막는다.

### A-7. 학습 표본 개월수 가중 — **채택 완료(2026-09-10)**

학습 목표는 "개점 후 월매출의 m개월 평균"인데 m이 매장마다 다르다(1개월 6곳, 11개월 27곳).
종전에는 전부 같은 무게로 학습했다 — 1개월치 한 장을 11개월 평균과 똑같이 믿는 셈이다.

**k는 적중률을 보고 고르지 않았다.** 가중식이 `k = σ²_월변동 / σ²_모형`이라고 말해주므로
둘을 각각 측정했다(0.02318 / 0.00942 = **2.46**).

| | MAPE | 중앙값 | ±10% | ±20% | 최악 |
|---|---:|---:|---:|---:|---|
| 가중 없음 | 10.129% | 9.11% | 20/38 | 34/38 | +26.9% |
| **k=2.46 ← 채택** | **9.881%** | **9.02%** | 20/38 | 34/38 | **+26.0%** |

- **적용됨**: `usageRevenue.ts`의 `MONTH_WEIGHTING_DEFAULT = 2.46`. 되돌리려면 `null`.
- **채택 판단**: 사전 등록 조건의 ±10%가 안 늘어 문자로는 미달이다. 근거는 **기전**이다 —
  같은 날 기각한 "어린 매장 잘라내기"는 하한선에 붙은 계수를 늘렸는데(사람이 정한 값으로
  후퇴), 가중은 6개→5개로 **줄인다**(먹거리 가시성이 바닥 0.0500→0.0537로 벗어남).
  데이터를 안 버리고 41곳을 다 쓰면서 데이터가 더 말하게 하는 방향이다. 나빠지는 지표 없음.
- **표본이 늘면 k를 다시 잴 것** — 하네스 "k를 데이터로 측정" 절이 세 숫자를 그대로 뽑아준다.
- 근거: `docs/releases/2026-09-10-month-weighting.md`

- 참고로 탄력성은 계속 내려오는 중이다 — 9/8 분리 이전 `요금^(1+c)`, c≥0.04(=1.04) → 분리 후 1.0
  → 이번 증거는 1.0보다 낮아야 함을 시사.

### C-3. 후보지 화면에 **실측 정확도** 표시 — **구현 완료(2026-09-10)**

**문제**: 의사결정이 일어나는 후보지 결과 화면은 예상매출을 **숫자 하나**로 보여주고, 참고범위는
`보수판단매출(85%)`·`상한참고매출(115%)`인데 이건 **설정값을 곱한 고정 밴드일 뿐 실측
신뢰구간이 아니다**. 실제 이 모형의 오차는 중앙값 9.1%, ±20% 안에 34/38곳이다. 화면만 보고
"68백만"을 단정적으로 받아들이면 출점 판단이 과신될 수 있다.

2026-09-10에 **이름 때문에 통계적 하한으로 오해하지 않도록 설명만 붙여뒀다**
("예측값 × 85% 고정 밴드 (실측 신뢰구간 아님)"). 근본 해결은 아래.

**설계(구현하면 이렇게)**
1. 검증화면이 이미 38곳 오차를 전부 계산한다. 계산 직후 요약 1건을
   `storeEvalSystemStatus/accuracy`에 upsert한다(쓰기 1건). 담을 것: `updatedAt`, `sampleCount`,
   `mape`, `medianAbsError`, `within10`, `within20`, 그리고 **실측 80%를 덮는 밴드 폭**.
2. `firestore.rules`에 그 문서만 회사계정 쓰기를 허용한다(다른 문서는 지금처럼 admin 전용):
   `match /storeEvalSystemStatus/{docId} { allow read: if isCompanyAccount();
    allow write: if isCompanyAccount() && docId == "accuracy"; }`
   — `cronSync` 문서는 admin SDK가 규칙을 우회하므로 영향 없다.
3. 후보지 결과 화면이 그 문서 **1건만** 읽어(읽기 비용 무시 가능) 예상매출 옆에 표시한다:
   "이 모형의 실측 오차: 중앙값 9.1% · 38곳 중 34곳이 ±20% 안 (2026-09-10 기준)".
   가능하면 고정 85/115 대신 **실측 80% 밴드**를 참고범위로 함께 보여준다.

**왜 이 설계인가**: 후보지 화면에서 검증을 다시 돌리면 읽기 800건이 더 든다(할당량 문제 재발).
요약 1건을 거쳐 가면 읽기 1건이면 된다. 갱신은 누군가 검증화면을 열 때 자동으로 된다.

**구현 상태(2026-09-10 밤)**: 위 설계 그대로 구현하고 규칙도 배포했다.
- `types.ts`에 `ModelAccuracySummary`, `store.ts`에 `getModelAccuracySummary`/`upsertModelAccuracySummary`
- `firestore.rules`: `storeEvalSystemStatus`는 회사계정 읽기 허용, **쓰기는 `accuracy` 문서만** 허용
  (`cronSync`는 admin SDK가 규칙을 우회하므로 영향 없음). 배포 완료·배포본 대조 확인.
- 검증화면: `coreSummary` 계산 직후 요약 1건 upsert(실패해도 화면은 그대로 동작)
- 후보지 결과화면: 그 1건만 읽어 예상매출 바로 밑에 표시 — 표본수·평균오차·중앙값·±10%·±20%,
  **평균 오차만큼 잡은 범위**, 그리고 "±15% 고정 밴드가 실제로는 몇 %만 덮는지"
- 요약이 아직 없으면(검증화면을 한 번도 안 열었으면) 안내 문구만 뜬다

**남은 확인**: 실제 화면을 눈으로 본 적은 없다. 검증화면을 한 번 연 뒤 후보지 결과화면에서

## 대비(명암비) 측정 방법 — 함정 세 가지 (2026-09-11)

전 화면을 두 테마로 훑으면서 **측정기 자체가 세 번 틀렸다.** 다시 잴 일이 있으면 이것부터 맞춰라.

**① 색 문자열을 파싱하지 마라. 픽셀을 읽어라.**
`getComputedStyle(el).color`는 `lab()`·`oklab()`으로 나올 수 있다. Tailwind의 불투명도
표기(`text-white/60`)와 일부 배경이 그렇다. 캔버스 `fillStyle`은 이 값을 **변환하지 않고
문자열 그대로 돌려준다.** 정규식으로 숫자를 뽑으면 `lab(95.2332 -0.0109673 5.82845)`이
`rgb(95, 0, 6)`(어두운 빨강)으로 읽혀서 **없는 실패가 무더기로 나온다.** 실제로 좌석배치도에서
"어두운 빨강 배경 위 어두운 글씨 7건"이라는 가짜 결과를 만들었다.

맞는 방법은 1×1 캔버스에 실제로 칠하고 `getImageData`로 픽셀을 읽는 것이다. 브라우저가
지원하는 모든 색공간이 sRGB 바이트로 나온다. 검산: `lab(95.2332 -0.0109673 5.82845)`
→ `#f5f1e6`(라이트 페이지 배경)이 나와야 한다.

**② 테마를 토글한 직후에 재지 마라.**
색에 transition이 걸려 있어 700ms로는 부족하다. 전환 중간값을 잡으면 라이트용 잉크가
다크 배경 위에 있는 것처럼 보인다(`#6b6459` on `#14120d` = 3.20 같은 가짜 실패 5건).
**1.5초는 기다리고 다시 재라.**

**③ 배경은 조상 체인을 합성해야 한다.**
반투명 배경(`bg-black/5`, soft 틴트)이 겹치면 실제 배경은 부모 색과 섞인 값이다.
불투명 배경을 만날 때까지 올라가서 바깥쪽부터 차례로 알파 합성한다. 특히
**soft 틴트를 깐 배지는 카드가 아니라 페이지 배경 위에 있을 때가 가장 불리하다** —
카드 기준으로만 계산하면 통과로 보인다.

### 판정 기준

본문 4.5:1, 큰 글씨(24px 이상 또는 18.66px 이상 굵게) 3:1. 아이콘·테두리 같은 비문자
요소는 3:1이다. **같은 색을 글씨와 배경 양쪽에 쓰는 경우를 조심하라** — 글씨용으로 밝히면
그 색을 배경으로 쓰는 배지의 흰 글씨가 깨진다. 그래서 토큰을 `--sl-gold`/`--sl-gold-ink`,
`--sl-step-*`/`--sl-step-*-ink`처럼 두 벌로 나눠 뒀다.

### 현재 상태

10개 화면 × 라이트/다크 = **미달 0건**(위 방법으로 재측정 완료). 애플리케이션 콘솔 오류도 0건.
