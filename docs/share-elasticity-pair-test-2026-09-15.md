## 0. 먼저 — 방문 1회 실측은 가동률로 못 쓴다

경쟁점 가동률 관련 필드는 셋이다.

| 필드 | 곳수 | 정체 |
|---|---:|---|
| `pingbotUtilization` | 54 | 30일 평균. **믿을 수 있다** |
| `measuredSeatRate` | 87 | `visitorCount ÷ totalPcCount` = **방문 순간 머릿수** |
| `visitorCount` | 103 | 위의 분자 |

`measuredSeatRate`가 실제로 방문 순간 머릿수라는 건 값으로 확인했다(링크피시방 65/200 = 32.5%,
기록된 실측 32.5%). 둘 다 있는 33곳에서 대조한 결과다.

```
핑봇 ↔ 실측   r = 0.219       (유의선 0.35)
실측/핑봇 비율 0.04 ~ 4.11배
```

시점 차이인가 싶어 갈랐더니 **최근 방문일수록 더 안 맞았다.**

```
2026년 방문   13곳   r = -0.147
2025년 이후   20곳   r =  0.065
2024년 이전   13곳   r =  0.374
```

시각대 보정으로도 안 된다(오전 0.70 / 낮 0.95 / 오후 1.76 / 저녁 1.87, 표본 2~14곳).

> **결론: 경쟁점 가동률은 핑봇만 쓴다.** 사용자 확인 — "핑봇 정확도는 괜찮은 편임. 차이 많이
> 안 남. IP 잘못 넣은 거 아니면." 핑봇은 **조회되는 곳을 이미 다 넣은 상태**라 54곳이 천장이다.

### 철회 — "총수요를 관측할 수 있다"는 앞선 결론은 틀렸다

핑봇+실측을 섞어 상권 19곳의 총수요를 만들고 "유동인구와 r=0.789로 설명된다"고 했는데,
분해해 보니 그게 아니었다.

```
총수요 ↔ 총 PC대수     r = 0.880    ← 가동률이 기여를 거의 안 한다
총 PC대수 ↔ 500m유동   r = 0.757
총수요   ↔ 500m유동    r = 0.789    ← 위 두 줄의 결과일 뿐
```

"관측 총수요"는 사실상 **그 동네에 PC가 몇 대 깔렸나**였고, 그건 수요 측정이 아니라 공급 사실이다.
핑봇만으로 상권 70% 이상을 덮는 상권은 **2곳**뿐이라 총수요 경로는 지금 닫혀 있다.

## 1. 그래서 짝(pair)으로 간다

총수요를 못 만들어도 **점유율 산식 자체는 배울 수 있다.** 같은 상권 안의 두 매장을 짝지으면
상권수요가 분자·분모에서 약분되기 때문이다.

```
log(가동률비) = b x log(경쟁력비)
```

`b`가 "경쟁력 → 점유율" 탄력성이다. 교과서식이 성립하려면 `b > 0`이고 유의해야 한다.

### 1-A. 자사 vs 경쟁점 — 45짝

```
r = 0.205   (유의선 0.30)   탄력성 b = 0.681
경쟁력비 범위 1.09 ~ 2.03배
우리가 열위인 짝: 0개
```

**열위 표본이 하나도 없다.** 38곳 전부 경쟁력격차 ≥ 1.0인 것과 같은 문제다. "경쟁력이 떨어지면
점유율이 얼마나 빠지나"를 배울 재료가 없다.

### 1-B. 경쟁점끼리 — 27짝, 상권 16곳

우리 매장을 빼고 경쟁점 둘씩 붙이면 양방향이 생긴다. 상권수요가 통제된다는 성질은 그대로다.

```
r = 0.144   (유의선 0.38)   탄력성 b = 0.346
경쟁력비 범위 0.65 ~ 1.49배
A가 열위인 짝 13개 / A가 우위인 짝 14개
```

**열위 표본 13개를 확보했는데도 종합 경쟁력점수는 가동률을 설명하지 못한다.**
즉 "열위 사례가 없어서 안 나온다"는 앞선 진단은 틀렸다.

## 2. 구성요소로 쪼개니 이유가 나왔다 — 서로 상쇄하고 있다

같은 27짝을 `computeCompetitorScores`의 4개 컴포넌트로 나눠 각각 쟀다.

| 항목 | 짝별 비율범위 | 가동률비와의 상관 | 탄력성 | 상권 하나씩 빼면 | 부호 |
|---|---|---:|---:|---|---|
| **사양** | 0.65~1.30배 | **+0.409** ← 유의 | 1.292 | 0.332 ~ 0.486 | 유지 |
| 시설 | 0.47~2.30배 | +0.313 | 0.401 | 0.110 ~ 0.375 | 유지 |
| 먹거리 | 0.67~1.50배 | +0.030 | 0.094 | −0.085 ~ 0.184 | **뒤집힘** |
| **입지** | 0.25~5.00배 | **−0.402** ← 유의 | −0.317 | −0.455 ~ −0.325 | 유지 |
| 종합(가중합) | 0.65~1.49배 | +0.144 | 0.346 | −0.062 ~ 0.251 | **뒤집힘** |
| (참고) PC대수비 | 0.40~4.76배 | +0.087 | — | — | — |

유의선 0.38. 상권 단위 leave-one-out 16회.

### 읽는 법

- **사양이 유일하게 안정적으로 살아남는다.** 탄력성 1.29 — 사양이 1.3배 좋으면 가동률이 1.4배.
- **입지 컴포넌트가 반대 방향이다.** `computeLocationScoreFromFacts`는 낮은 층에 높은 점수를
  주는데(1~2층·지하1~2층 4점 / 6층 이상 0점 / 엘리베이터 +1), 같은 상권 안에서는 **점수가 높은
  쪽이 가동률이 낮다.**
- 이 둘이 상쇄해서 **종합 점수가 0이 된다.** 종합만 보면 "경쟁력은 무의미하다"로 보이는데,
  실제로는 신호가 있는 항목과 거꾸로 된 항목이 섞여 지워진 것이다.
- 먹거리는 부호가 뒤집힌다. 쉐프앤클릭 자체 브랜드라 변별이 적은 건 의도된 설계이므로
  (사용자 확인, 2026-09-15) 이 결과는 설계와 모순되지 않는다.

## 3. 아직 고치지 않는 이유 — 기존 결과와 충돌한다

입지 부호를 뒤집고 싶어지지만, **정반대 방향의 기존 근거가 있다.**

| 근거 | 방향 |
|---|---|
| 자사 접근가시성을 매출에 곱하게 한 변경(`accessScoreMode: visibility-x-preemption`) | 낮은 층 = 좋다 → MAPE 10.00 → 9.37% 개선 |
| 기존 38곳 층수 규칙이 평가자 점수를 92% 재현 | 낮은 층 = 좋다 |
| 이번 경쟁점 27짝 | 낮은 층 = **나쁘다** |

둘 다 맞을 수는 없다. 그런데 셋 중 어느 쪽도 지금 결정적이지 않다. 그래서 **산식·설정값은
이번에 하나도 바꾸지 않았다.** 판단 근거만 남긴다.

가능한 설명(검증 안 됨):
- 자사 `visibilityScore`는 평가자가 로드뷰·현장에서 본 것을 넣은 값이라, 층수만이 아니라
  간판·코너·보행노출을 함께 담고 있을 수 있다. 경쟁점 입지는 층수+엘베로만 자동 계산된다.
  **같은 이름이지만 다른 것을 재고 있을 가능성**이 가장 크다.
- 상층 매장이 임대료가 싸서 더 넓고 새것일 수 있다. 다만 짝 내 PC대수비는 r=0.087로 무관했다.

## 4. 한계 — 이 결과를 그대로 settings에 넣지 말 것

- **27짝은 서로 독립이 아니다.** 한 상권이 짝을 여러 개 내놓고, 같은 경쟁점이 여러 짝에 들어간다.
  실효 표본은 27보다 작다. 유의선 0.38은 낙관적인 수치다.
- **5개 항목을 봤으므로 다중검정 보정이 안 돼 있다.** 하나쯤 우연히 유의할 수 있다.
  다만 사양(+)과 입지(−)는 leave-one-out 16회 전부 부호가 유지됐다.
- 경쟁점 스펙 결측이 많다(모니터 43%, VGA상위 27%, 리뉴얼연도 10%). 사양 컴포넌트는
  `applySurveyLevelDefault`로 기본값이 채워진 곳이 섞여 있다.
- 핑봇 자체를 독립 검증한 적이 없다. **자사 매장은 경쟁점 목록에 0곳**이라 대조군이 없다.
  핑봇에서 자사 가맹점이 조회되면 실제 가동률과 바로 대조할 수 있다 — 비용 0.

## 5. 방법 (하네스 재생성용)

```
node .local-tools/dump-validation-snapshot.mjs
npx vitest run src/lib/storeEval/_pairShare.test.ts --reporter=verbose
```

세 가지를 잰다.

1. 자사 vs 경쟁점 짝 — `prepareExistingStoresForEvaluation`의 `competitivenessScore` 대
   `computeCompetitorScores(c, settings).total`, 가동률은 자사 월평균(소수) 대 핑봇(퍼센트).
   **단위가 다르다 — 자사 `utilizationRate`는 0.13, 경쟁점 핑봇은 32.5다.**
2. 경쟁점끼리 짝 — 같은 `candidateCode` 안에서 핑봇이 있는 경쟁점 2곳 이상. 방향은 등록
   순서로 고정한다(점수 높은 쪽을 앞에 두면 부호가 한쪽으로 쏠린다).
3. 구성요소별 — 한 항목이라도 결측인 짝은 모든 항목에서 뺀다(공정 비교). 상권 단위
   leave-one-out으로 부호 안정성을 본다.
