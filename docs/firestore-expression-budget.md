## 이번에 남긴 변경

`firestore.rules`의 `isValidCompetitor`에서 선택 필드 23개의 wrapper 호출만 펼쳤다.
필드가 없으면 허용하고, 있으면 기존 nullable 타입·문자열 길이·숫자 범위를 그대로 검사한다.
허용 키, 필수 키, 회사 인증, 작성 시각 및 관계 불변성 규칙은 동일하다.
**경쟁점 저장 전체가 해결된 것은 아니다.** 실제 값을 채운 신규 회귀 사례는 여전히 실패한다.

실험한 동일 필드 목록 중복 제거와 배열 끝 이후 검사 생략은 기존 실패를 추가로 해결하지 못했다.
이 실험 변경은 모두 되돌렸다. 다른 파일의 기존 미커밋 변경은 유지했다.

## 다음 구현 단위

단순 helper 축약만으로 해결됐다고 판단하지 않는다. 먼저 좌석 프로젝트/설정처럼 중첩 배열이
많은 쓰기를 대상으로, 저장 구조 분할과 서버 검증 경유 중 앱 호환성이 나은 방식을 설계한다.
현재 `src/lib/seatLayout/store.ts`의 `saveProject`는 클라이언트 `setDoc`를 사용한다.

서버 검증 경유를 선택한다면 다음을 하나의 완료 단위로 묶는다.

1. 현재 전체 스키마의 키·타입·길이·범위·배열 원소 검사를 서버 validator로 옮기고
   정상 최대 크기 및 마지막 원소 오염 테스트를 만든다.
2. `src/lib/server/companyAuth.ts`의 검증된 회사 인증을 재사용하고,
   작성자 UID는 요청 본문이 아니라 인증 토큰에서 결정한다.
3. 업데이트의 기존 문서를 트랜잭션에서 읽어 불변성·시각 조건을 보존한다.
4. 브라우저 저장 경로를 새 API로 연결하고 직접 클라이언트 쓰기는 규칙에서 차단한다.
   Admin SDK는 규칙을 우회하므로 서버 검증이 빠진 상태로 전환하지 않는다.
5. API 권한/스키마 공격, 실제 저장·재조회, 경계 크기, 실패 표시를 모두 확인한다.
   이후 결과·이력·업로드의 중첩 snapshot 검증을 같은 방식으로 별도 처리한다.
