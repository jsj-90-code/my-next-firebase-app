# 아이센스 운영데이터 수신서버 기능명세 (초안)

- 작성: 아이센스 PC가맹부 · 2026-11-04
- 대상: 엔미디어플랫폼 플랫폼사업팀·개발팀
- 근거: 귀사 회신(2026-11-04) "1. 기술 검토 내용"과 "2. 확인 및 자료 요청"
- 상태: **초안** — 양사 협의로 합의되면 확정본으로 바꿉니다. 규격 판(schemaVersion)은 `"1"`입니다.

---

## 1. 요약

| 항목 | 내용 |
|---|---|
| 방향 | 게토 가맹점 카운터 PC → 아이센스 수신서버 (매장이 먼저 접속, 귀사 서버 안 거침) |
| 연결 | TCP, 접속을 유지해도 되고 보낼 때만 접속해도 됨 |
| 암호화·인증 | **Noise_XK_25519_ChaChaPoly_SHA256** (TLS 미사용, 귀사 안 수용) |
| 매장 식별 | 매장 PC가 스스로 만든 고정키(X25519) + 첫 접속 때 1회용 **등록토큰**으로 매장과 묶음 |
| 자료 단위 | (매장, 자료 종류, 집계 시작~종료) 한 묶음 = 메시지 하나 |
| 수신 확인 | 메시지마다 ACK. ACK 없으면 다음 전송 때 재전송 |
| 중복 | 같은 묶음은 아이센스가 덮어씀 (revision 큰 쪽이 이김) |
| 개인정보 | 회원 ID·이름·카드번호 등 식별정보 제외. 회원 구분은 **가명 회원키**로 (4.2절) |

## 2. 접속 정보

| 구분 | 주소 | 포트 | 서버 공개키 |
|---|---|---|---|
| 운영 | `isens-1544.asuscomm.com` | 19000/TCP | 별도 전달 (운영 키) |
| 개발 | `isens-1544.asuscomm.com` | 19000/TCP | 별도 전달 (개발 키) |

- **개발과 운영은 같은 주소·포트를 쓰고, 서버 공개키로 구분합니다.** 개발 키로 접속한 자료는 운영 자료와 완전히 따로 저장되고, 매장 등록부도 따로 씁니다.
  개발 시험은 개발 키로 자유롭게 하시면 됩니다.
- 접속 제한
  - 접속하는 매장 IP가 제각각이라 **IP 허용목록은 쓰지 않습니다.** 대신 Noise 인증(서버 키 + 매장 키)을 통과하지 못하면 바로 끊습니다.
  - 핸드셰이크는 접속 후 15초 안에 끝나야 합니다.
  - 15분 동안 아무 메시지가 없으면 서버가 연결을 닫습니다. 연결을 유지하려면 5분마다 `ping`을 보내십시오.
  - 같은 IP에서 10분 동안 인증 실패가 20번이면 그 IP를 1시간 막습니다.
  - 매장 하나당 동시 연결은 5개까지, 메시지 하나는 32MB까지, 하루 500MB까지입니다.

## 3. 통신 규격

### 3.1 틀(프레이밍)

모든 Noise 메시지 앞에 **2바이트 길이(빅엔디언)** 를 붙입니다. Noise 명세가 TCP에 권하는 방식이며, 메시지 하나는 최대 65,535바이트입니다.

```
[길이 2바이트 BE][Noise 메시지]
```

### 3.2 핸드셰이크

- 프로토콜 이름: `Noise_XK_25519_ChaChaPoly_SHA256` (Noise Protocol Framework rev 34)
- 프롤로그: ASCII `ISENS-GETTO/1` (13바이트)
- 역할: 매장 = initiator, 서버 = responder. 매장은 서버 공개키(`rs`)를 미리 압니다.

| 순서 | 방향 | Noise 토큰 | 담는 내용 |
|---|---|---|---|
| 1 | 매장 → 서버 | `e, es` | 빈 payload |
| 2 | 서버 → 매장 | `e, ee` | 빈 payload |
| 3 | 매장 → 서버 | `s, se` | **hello** (UTF-8 JSON, 아래) |

```json
{
  "type": "hello",
  "storeId": "20160311018",
  "enrollToken": "첫 접속 때만 — 아이센스가 발급한 등록토큰",
  "client": { "name": "게토 카운터", "version": "x.y.z" },
  "schemaVersion": "1"
}
```

서버는 hello를 확인한 뒤 첫 전송 메시지로 `welcome` 또는 `error`를 보냅니다.

```json
{ "type": "welcome", "env": "prod", "storeId": "20160311018", "serverTime": "2026-11-04T16:00:00.000+09:00", "schemaVersion": "1", "keySlot": "current" }
{ "type": "error", "code": "E_AUTH", "message": "...", "retryable": false }
```

- 서버 공개키가 틀리면 1번 메시지에서 끊깁니다.
- 참고: 아이센스 쪽 구현은 cacophony 공식 시험값(`Noise_XK_25519_ChaChaPoly_SHA256`)과 바이트 단위로 일치하는 것을 확인했습니다. 시험용 매장 프로그램(Node.js)도 요청하시면 드립니다.

### 3.3 전송 단계 — 응용 메시지

- 응용 메시지 하나 = UTF-8 JSON 하나
- 65,535바이트를 넘으면 여러 Noise 전송 메시지로 나눕니다. 각 전송 메시지의 평문은 `[표시 1바이트][조각]`입니다.
  - `0x00` = 조각이 더 있음, `0x01` = 마지막 조각
  - 조각들을 순서대로 이어 붙이면 JSON 하나가 됩니다. 한 조각의 최대 크기는 65,518바이트입니다(65,535 − 태그 16 − 표시 1).
- 전송 단계 AEAD의 추가 데이터(AD)는 비웁니다.
- Noise nonce는 방향별로 0부터 1씩 오릅니다. 순서가 어긋나면 복호화가 실패하고 서버는 연결을 끊습니다(다시 접속하면 됨).

### 3.4 메시지 종류

**매장 → 서버**

| type | 용도 |
|---|---|
| `data` | 자료 한 묶음 (4장) |
| `ping` | 연결 유지 → 서버가 `pong`으로 답함 |

`data` 공통 머리:

```json
{
  "type": "data",
  "msgId": "UUID 등 매장 안에서 겹치지 않는 값 (1~100자)",
  "storeId": "20160311018",
  "kind": "sales",
  "periodStart": "2026-11-03T09:00:00+09:00",
  "periodEnd":   "2026-11-04T09:00:00+09:00",
  "revision": 0,
  "generatedAt": "2026-11-04T09:05:12+09:00",
  "payload": { }
}
```

- `periodStart`/`periodEnd`: 매장별 집계 시작·종료 시각(영업일 마감 기준). ISO 8601이며 **시간대를 반드시** 넣습니다(`+09:00`).
- `revision`: 처음 마감은 0, 정산·재결산으로 같은 기간을 다시 보내면 1, 2, … 로 올립니다.
- `storeId`는 hello에서 인증된 매장과 같아야 합니다.

**서버 → 매장: ACK**

```json
{ "type": "ack", "msgId": "...", "ok": true,  "status": "stored", "revision": 0, "sha256": "..." }
{ "type": "ack", "msgId": "...", "ok": false, "code": "E_SCHEMA", "message": "...", "retryable": false }
```

### 3.5 ACK·재전송·중복 처리

중복 판정 열쇠는 **(storeId, kind, periodStart, periodEnd)** 입니다.

| status | 뜻 | 매장이 할 일 |
|---|---|---|
| `stored` | 새로 저장했거나 덮어씀 | 전송 완료 처리 |
| `unchanged` | 같은 열쇠·같은 revision·같은 payload가 이미 있음 (재전송) | 전송 완료 처리 |
| `superseded` | 더 큰 revision이 이미 있어 이번 것은 버림 | 전송 완료 처리 |

- 덮어쓰기 규칙: 새 revision이 저장된 것보다 크거나 같으면 새 것으로 덮어씁니다. 작으면 버립니다.
- 서버는 최신값과 별도로 **받은 원문을 전부** 보관합니다. 재전송분도 포함됩니다.
- 재전송: `ok:true` ACK를 받지 못한 메시지(시간 초과 60초, 연결 끊김 포함)는 다음 전송 때 다시 보냅니다. `msgId`는 새로 써도 되고 그대로 써도 됩니다.

**오류 코드**

| code | 뜻 | retryable | 매장이 할 일 |
|---|---|---|---|
| `E_HANDSHAKE` | 핸드셰이크 실패(공개키·프롤로그·프로토콜 이름 불일치) | – | 설정 확인. 연결이 끊김 |
| `E_AUTH` | 등록 안 된 매장 / 키 불일치 / 토큰 틀림 | 아니오 | 토큰 재발급 요청 |
| `E_TOKEN_EXPIRED` | 등록토큰 기한 지남 | 아니오 | 토큰 재발급 요청 |
| `E_REVOKED` | 폐기된 매장 | 아니오 | **전송 중지** |
| `E_FORMAT` | JSON이 아니거나 틀 오류 | 아니오 | 고친 뒤 새로 전송 |
| `E_SCHEMA` | 머리 항목 오류(시각 형식 등) | 아니오 | 고친 뒤 새로 전송 |
| `E_STORE_MISMATCH` | storeId가 인증된 매장과 다름 | 아니오 | 고친 뒤 새로 전송 |
| `E_TOO_LARGE` | 메시지 32MB 초과 | 아니오 | 나눠서 전송 |
| `E_QUOTA` | 매장 하루 용량 초과 | **예** | 다음 날 재전송 |
| `E_SERVER` | 서버 저장 실패 | **예** | 나중에 재전송 |
| `E_TOO_MANY` | 매장 동시 연결 초과 | – | 연결 수 줄이기 |
| `E_DECRYPT` | 전송 메시지 복호화 실패 | – | 다시 접속 |

## 4. 자료 범위 (`kind`별 payload)

### 4.1 집계 자료로 분석이 가능한지에 대한 답

- **하루 합계만 받으면 저희 분석 목적(가동률·좌석 선호도)을 이룰 수 없습니다.**
  가동률은 시간대별로, 좌석 선호도는 좌석별로 봐야 하기 때문입니다.
- 그래서 **좌석별 이용 내역(`sessions`)** 을 우선 요청드립니다. 식별정보는 빼고, 회원은 가명키로 받습니다.
  이용 내역 제공이 어렵다면 최소한 **좌석별·시간대별 집계(`seat_hourly`)** 가 필요합니다.
- 구역별 집계와 가맹점 매칭은 귀사 안대로 아이센스가 합니다. 이를 위해 좌석 목록(`seats`)이 필요합니다.

### 4.2 회원 구분 — 가명 회원키

재방문·이용 빈도 분석을 위해 **회원 구분은 필수입니다.** 다만 회원 ID·이름은 받지 않습니다.
아래 가명 회원키 방식을 제안드리며, 이 방식이 어렵다면 귀사가 제안하는 다른 방식이라도 **같은 회원을 같은 값으로 알아볼 수 있어야** 합니다.

- `memberKey` = HMAC-SHA256(**귀사만 보관하는 비밀값**, 게토 회원 고유번호)을 소문자 hex 64자로 표현한 값
- 같은 회원은 **모든 매장·모든 날짜에서 같은 키**가 되도록 비밀값 하나를 공통으로 써 주십시오. 비밀값은 아이센스에 주지 않습니다. 저희는 키에서 원래 ID를 알아낼 수 없습니다.
- 비밀값을 바꾸면 회원 구분이 끊기므로, 바꿀 때는 미리 알려 주십시오.
- 비회원·임시 카드는 `memberKey: null`, `memberClass: "guest"`로 보냅니다.
- 가명키도 법적으로는 가명정보에 해당할 수 있어, 매장 동의서(7장)에 이 항목을 포함합니다.

### 4.3 자료 종류

| kind | 보내는 때 | 기간(periodStart~End) | 필수 |
|---|---|---|---|
| `seats` | 매일 마감 후 | 마감 영업일 | 필수 |
| `sessions` | 매일 마감 후 | 영업일 | **우선 요청** |
| `seat_hourly` | 매일 마감 후 (`sessions`를 못 줄 때) | 영업일 | 대안 |
| `sales` | 매일 마감 후 + 정산·재결산 때(revision↑) | 영업일 | 필수 |
| `games` | 매일 마감 후 | 영업일 | 필수 |
| `store_daily` | 매일 마감 후 | 영업일 | 필수 |

**`seats`** — 좌석 목록

```json
{ "seats": [ { "seatNo": "12", "areaName": "커플석", "active": true } ] }
```

**`sessions`** — 좌석 이용 내역 (한 번 앉았다 일어난 것이 한 줄)

```json
{ "sessions": [ {
    "seatNo": "12",
    "start": "2026-11-03T13:02:00+09:00",
    "end":   "2026-11-03T15:40:00+09:00",
    "memberKey": "hex 64자 또는 null",
    "memberClass": "member | guest | 기타(귀사 분류명)",
    "chargeType": "time | fixed | postpaid | 기타(요금 방식)",
    "usedAmount": 3000,
    "games": [ { "name": "리그 오브 레전드", "minutes": 150 } ]
} ] }
```

- `usedAmount`: 그 이용에 차감·결제된 PC 이용 금액(원, 부가세 포함). 정액권처럼 금액이 없으면 0과 `chargeType`으로 구분합니다.
- 좌석 이동은 이동 전과 후를 각각 한 줄로 보냅니다.
- `games`는 게임 이용 자료를 이용 단위로 줄 수 있을 때만 넣습니다. 어렵다면 빼고 `games` 종류로 대신합니다.

**`seat_hourly`** — `sessions` 대안

```json
{ "rows": [ { "seatNo": "12", "hour": "2026-11-03T13:00:00+09:00", "usedMinutes": 58, "sessions": 1, "uniqueMembers": 1 } ] }
```

**`sales`** — 마감·정산 매출 (원, 부가세 포함, 키오스크·카운터 POS에 기록된 그대로)

```json
{
  "pcSales": 412000, "foodSales": 233500, "otherSales": 0,
  "discount": 12000, "refund": 0,
  "payment": { "cash": 50000, "card": 583500, "etc": 0 },
  "foodByCategory": [ { "category": "라면", "amount": 45000, "count": 9 } ],
  "closedAt": "2026-11-04T09:00:00+09:00",
  "settlementNote": "재결산 사유(있을 때)"
}
```

- `pcSales`: 요금 충전·시간 판매 매출. 회원 적립금·쿠폰 사용분은 `discount`에 넣습니다. 귀사 마감 화면 기준과 다르면 항목명은 귀사 기준을 따르고 정의만 알려 주십시오.
- `foodByCategory`는 선택입니다.

**`games`** — 게임별 하루 이용

```json
{ "games": [ { "name": "리그 오브 레전드", "minutes": 8420, "sessions": 71, "uniqueMembers": 52 } ] }
```

**`store_daily`** — 매장 하루 요약

```json
{ "visitors": 183, "uniqueMembers": 141, "guestSessions": 22, "newMembers": 9, "openSeats": 80 }
```

- 모르는 `kind`를 보내도 서버는 저장합니다(`stored`). 항목을 늘릴 때는 아래 6장 절차를 따릅니다.

## 5. 서버 키·매장 키 운용

### 5.1 서버 공개키

- 운영용과 개발용 공개키(32바이트, hex·base64)와 지문을 **이 문서와 별도로** 전달드립니다. 받으신 뒤 지문이 맞는지 양사 담당자가 한 번 맞춰 봅니다.
- 갱신: 바꾸기 **30일 전**에 새 공개키를 드립니다. 그 기간에는 서버가 옛 키와 새 키를 모두 받습니다. 매장 프로그램이 새 키로 다 바뀌면 옛 키를 끕니다.
- 유출이 의심되면 즉시 새 키로 바꾸고 알려 드립니다.

### 5.2 매장 키와 등록토큰

1. 매장 카운터 프로그램이 처음 실행될 때 X25519 고정키를 스스로 만들어 매장 PC에만 보관합니다. **개인키는 매장 밖으로 나가지 않습니다.**
2. 아이센스가 동의 매장마다 **등록토큰**(1회용, 30일 유효)을 발급해 귀사에 `storeId ↔ 토큰` 목록으로 전달합니다. 목록은 암호를 걸어 전달하고, 암호는 따로 전달드립니다.
3. 매장 프로그램이 첫 접속 hello에 토큰을 넣으면, 서버가 그 매장 키를 해당 `storeId`에 묶고 토큰을 지웁니다. 다음 접속부터는 토큰이 필요 없습니다.
4. 카운터 PC를 바꾸거나 프로그램을 다시 설치해 키가 바뀌면 토큰을 다시 발급합니다. 새 키가 묶이면 옛 키는 자동으로 못 쓰게 됩니다.
5. 폐기: 동의 철회나 가맹 해지 때 아이센스가 그 매장을 폐기합니다. 다음 접속부터 `E_REVOKED`를 받으며, 이때 매장 프로그램은 **전송을 멈추고 쌓인 자료도 보내지 않아야** 합니다. 폐기한 매장은 귀사에도 알려 드립니다.

- `storeId`는 **아이센스 가맹점코드**(11자리 숫자, 예: 20160311018)를 씁니다. 대상 매장의 가맹점코드·매장명 목록을 별도로 드리니, 각 매장 카운터 프로그램에 이 코드를 넣어 주십시오. 따로 대응표를 주고받을 필요가 없습니다.

## 7. 매장 동의

- 동의서 양식 작성과 가맹점 동의 받기는 **아이센스가 맡습니다.** 양식은 내부 검토 뒤 공유드립니다.
  - 동의서 내용: 제공 항목(4장), 가명 회원키, 목적(가맹점 운영 분석), 보관 기간, 철회 방법
- 동의가 끝난 매장은 **가맹점코드·매장명·동의일** 목록으로 드리고, 그 매장들의 등록토큰을 발급합니다.
- 1차는 동의 매장 몇 곳으로 시범 운영한 뒤 넓히는 것을 제안합니다.
