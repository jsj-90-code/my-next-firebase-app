## 1. ⭐⭐ 다음 세션이 제일 먼저 알아야 할 것 — 되짚기의 대표성 결함

`_quickEvalBias.test.ts`는 기존점의 **조사된** 경쟁점으로 돈다: 중앙 **4곳** · 최대 10곳.

⛔ **여기서부터는 내 추측이고 측정한 적이 없다** — "실제 후보지는 카카오가 10~20곳을 찾는다"
   고 적었는데 **근거가 없다.** 호구포역점은 카카오로도 **1곳**이었다(사용자 확인).
   이 가정이 틀리면 아래 "대표성 결함" 진단 자체가 무너진다.

### ⭐ 다음 세션 첫 작업 — 이 가정부터 확인하라

1. 후보지 13곳의 주소로 **카카오 500m PC방 수집을 실제로 돌려**, 저장된 조사 경쟁점 수와
   나란히 놓는다(`quickEval/kakaoPcBangs.ts` 사용. 카카오 키 필요, 무료 할당량).
2. **정말 더 많이 찾으면** → 되짚기를 카카오 경쟁점 수에 맞춰 고친다.
3. **별로 안 다르면** → "되짚기 대표성 결함"이라는 내 진단은 **틀린 것**이다. 그러면 −45%는
   자사 사양 하나로 충분히 설명되고(0-1절), 되짚기를 고칠 이유가 없다.

⚠️ 어느 쪽이든 **먼저 재고 나서** 판단하라. 오늘 나는 이 순서를 안 지켜서 세 번 틀렸다.

⚠️ 다만 위 0-1절대로, **호구포 −45%의 원인은 이게 아니었다**(경쟁점 1곳). 이 결함은
여전히 사실이지만 그 사건의 설명은 아니다.

경쟁점을 건드리는 변경은 전부 이 차이만큼 **과소평가된다.** 오늘 −10.4%로 잰 게 실제
−45%였다(4배 넘게). 경쟁점 수별로 갈라 봐도 10곳+에서 −11.9%였다 — **10곳 너머를 아예
못 쟀다.**

⛔ **경쟁점을 건드리려면 카카오 경쟁점 수를 반영한 되짚기부터 만들어라.** 지금 되짚기로 잰
숫자는 실제 후보지에 적용할 수 없다.

## 3. ⭐ 다음 주제 — 모바일 대응

> **2026-09-23 저녁 반영(page.tsx만, 산식 무관).** viewport는 문제 아니었다 — Next.js가 기본으로
> `width=device-width, initial-scale=1`을 항상 넣는다(`node_modules/next/dist/docs/01-app/01-getting-started/14-metadata-and-og-images.md` "Default fields").
> 고친 것: 입력 줄을 휴대폰에서 6칸 격자로(주소 / 대수·요금 / 지상·층·엘베 / 조회), 입력칸 글씨
> 16px(iOS 확대 방지), 표 둘을 sm 미만에서 카드 목록으로, 결과 숫자 2열.
> ⚠️ **여전히 실제 기기로는 안 봤다**(로그인 관문). 휴대폰으로 한 번 보고 어색한 곳을 알려 달라.

(아래는 반영 전 점검 기록)

사용자: *"이거 주소만초기평가 모바일 호환되나?"*

### 확인한 것 (정적 점검만, 실제 기기로 안 봤다)

**⚠️ 제일 큰 의심 — `viewport` 설정이 없다.**
`src/app/layout.tsx`에 `export const viewport`가 **없다**(grep으로 확인). Next.js App Router는
기본 viewport를 넣어 주지만, 명시가 없으니 **실제 기기에서 먼저 확인할 것.** 없으면 모바일이
데스크톱 폭으로 그려서 글씨가 작게 나온다.

**괜찮아 보이는 것**
- 껍데기: `mx-auto w-full min-w-0 max-w-5xl px-4` — 좌우 여백·폭 정상
- 입력 줄: `flex flex-wrap`, 주소는 `min-w-[260px] flex-1` → 좁아지면 줄바꿈
- 결과 통계: `sm:grid-cols-2 lg:grid-cols-4` → 모바일 1열

**불편할 것**
- 표 둘이 `min-w-[620px]` / `min-w-[520px]` + `overflow-x-auto` → **가로 스크롤**. 동작은 하지만
  손가락으로 밀어야 한다. 카드형으로 바꾸는 걸 검토
- 입력칸 고정폭들(110/120/92/72/96px)이 아주 좁은 화면에서 어떻게 접히는지 확인 필요

**⚠️ 실제로 안 봤다.** 이 도구는 로그인 관문이 있어 브라우저 도구로 확인하지 못했다.
**기기(또는 개발자도구 모바일 모드)로 직접 보고 시작하라.**

## 4. 알아 둘 것

- **빌드**: `npm run build`만 치면 된다(package.json에 힙 박아 뒀다). 타입검사만은 `npm run typecheck`
- **배포 확인**: Vercel MCP `list_deployments`에 `projectId`만 넘겨라. **`teamId`를 같이 넘기면 403**이 난다
- **측정 시험**: `npx vitest run <파일> --disable-console-intercept`.
  ⚠️ `--reporter=basic`은 이 vitest에 없다 — 붙이면 **exit 0으로 조용히 실패**한다
- `tsc` 메모리·시간을 잴 땐 `--incremental false`(안 붙이면 캐시된 값으로 엉뚱한 결론)
- **AI 두 개를 구분하라**: 입지평가 초안(수집 때, **유료** 키, 가시성을 매겨 **산식에 들어간다**)
  vs AI 평가문(조회 후, 무료 티어, **산식에 안 들어간다**)
- 가시성 AI 채점 오차는 **안 재기로 확정**(2026-09-23) — 주소만으로는 AI 말고 방법이 없어
  오차를 알아도 바꿀 선택지가 없다. 다시 제안하지 마라

## 5. 오늘 내가 틀린 것 (같은 실수 반복 금지)

1. **대표성 없는 측정에 기대어 산식을 세 번 바꿨다.** 되짚기가 좋아 보인다고 채택했는데
   실사용에서 정반대로 깨졌다. 사용자가 세 번 짚어줘서야 잡았다.
2. **"지금도 10.5% 높다"며 두 번 말렸다.** 그 근거(되짚기 배율)가 실제 후보지엔 적용되지
   않는 값이었다.
3. **"이 도구는 줄 세우기용"이라고 계속 말했는데 틀렸다.** 사용자: *"순서를 구분할려는게
   아니다. 그냥 점포개인별 평가할뿐이야."* → **절대 금액 정확도가 핵심 지표**다.
   순서 논거로 배율 문제를 덮지 마라.
4. 추측을 측정으로 확인하지 않고 넘어갔다("경쟁점이 세지는데 매출 오르는 건 재학습 탓"
   → 학습 고정하고 재니 제대로 내려갔다).
