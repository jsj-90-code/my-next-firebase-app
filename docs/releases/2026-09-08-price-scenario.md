# 이용시간 고정 요금 변경 계산

PC 요금을 바꿔 주 예측값을 비교하면, PC 이용시간을 고정한 매출 변화와 다른 결과가 나온다. 주 예측은 총매출에 log(요금)의 학습 계수를 적용하므로 PC매출의 선형 변화를 보장하지 않는다. 이 회귀 반응을 할인으로 인한 고객 증가의 근거로 사용할 수 없다.

후보지 결과와 기존점 검증 화면에 접이식 요금 변경 계산을 추가했다. 기준 PC매출·먹거리 매출·기준요금·변경요금을 입력받아 `PC매출 × 변경요금 / 기준요금 + 먹거리 매출`을 계산한다. 초기 매출 구성은 현재 예측값과 설정상 먹거리 비중을 사용한 가정이라고 표시하며 실제 수치로 수정할 수 있다. 고객 수요 증가를 임의로 더하거나 기존 고정 상품비율 가동률 상한을 다시 적용하지 않는다. 이용시간을 고정하면 요금 변경 자체로 좌석 점유가 증가하지 않기 때문이다.

- 예시: PC 3,500만원 + 먹거리 3,500만원, 1,500원 → 1,000원. 결과 58,333,333원, 감소 11,666,667원.
- 주 예측·학습·검증 산식과 운영 자료는 변경하지 않았다. 계산기 입력도 저장하지 않는다.
- 2026-09-07T08:36:17.838Z 보관 자료로 송도점의 기존점 검증 경로를 재현했다. 1,500원 65,605,644원 → 1,000원 60,226,298원, 감소 5,379,346원. 같은 기준매출을 50:50으로 나눈 이용시간 고정 계산은 54,671,370원이다. 최신 운영 수치나 실제 요금 변경 후 실적이 아니다.
- 별도 브라우저 조회의 송도점 기본 예측은 66,051,335원으로 보관 자료와 달랐다. 예시의 7,000만원 및 50:50 구성은 실제 송도점 구성이라고 단정하지 않는다.
- Claude 독립 검토의 횡단면 회귀와 동일 점포 가격 시나리오 구분은 채택했다. 기본 설정의 회귀/중앙값 0.8/0.2를 운영값으로 본 설명과 역산한 표준편차는 채택하지 않았다. 보관 설정은 1/0이다. 상품매출을 고정하면 상품 비중이 달라지므로 기존 고정 비중 기반 가동률 상한을 재적용하자는 제안도 채택하지 않았다.
- 이전 검토의 수동 동기화 스크립트 `candidateCode` 불일치도 수정했다. 원본 후보지 코드 우선 연결을 cron과 맞추고 기존 문서 ID는 유지한다.

검증: 일반 테스트 18파일 442개, 보관 자료 재현 테스트 1개, TypeScript, 변경 파일 ESLint, 프로덕션 빌드, diff 검사 통과. 로컬 검증 화면에서 송도점 선택 및 위 예시의 결과를 실제 입력으로 확인하고 화면 배치도 확인했다. 후보지 결과 화면은 자동 저장되므로 열지 않았다. 운영 배포와 실제 동기화는 수행하지 않았다.

후속: 주 예측에 요금의 직접 효과를 반영하려면 기준 이용량을 정하는 방식과 PC·먹거리 매출 분리, 과거 실적과 당시 적용 요금의 대응부터 정해야 한다. 현재 요금 하나를 과거 전체 매출에 붙여 학습하거나 요금 계수 하한을 임의로 높이는 방식으로 해결됐다고 보지 않는다.
