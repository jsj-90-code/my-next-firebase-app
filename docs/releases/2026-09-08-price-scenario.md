# 이용시간 고정 요금 변경 계산

후속 상태: 사용자의 요금 우선 적용 요청에 따라 주 예측에도 직접 효과를 연결했다. 현재 구현과 검증은 [요금 직접 반영 모형 적용](2026-09-08-tariff-model.md)을 따른다. 아래는 계산기만 추가했던 단계의 기록이다.

PC 요금을 바꿔 주 예측값을 비교하면, PC 이용시간을 고정한 매출 변화와 다른 결과가 나온다. 주 예측은 총매출에 log(요금)의 학습 계수를 적용하므로 PC매출의 선형 변화를 보장하지 않는다. 이 회귀 반응을 할인으로 인한 고객 증가의 근거로 사용할 수 없다.

후보지 결과와 기존점 검증 화면에 접이식 요금 변경 계산을 추가했다. 기준 PC매출·먹거리 매출·기준요금·변경요금을 입력받아 `PC매출 × 변경요금 / 기준요금 + 먹거리 매출`을 계산한다. 초기 매출 구성은 현재 예측값과 설정상 먹거리 비중을 사용한 가정이라고 표시하며 실제 수치로 수정할 수 있다. 고객 수요 증가를 임의로 더하거나 기존 고정 상품비율 가동률 상한을 다시 적용하지 않는다. 이용시간을 고정하면 요금 변경 자체로 좌석 점유가 증가하지 않기 때문이다.

- 예시: PC 3,500만원 + 먹거리 3,500만원, 1,500원 → 1,000원. 결과 58,333,333원, 감소 11,666,667원.
- 주 예측·학습·검증 산식과 운영 자료는 변경하지 않았다. 계산기 입력도 저장하지 않는다.
- 2026-09-07T08:36:17.838Z 보관 자료로 송도점의 기존점 검증 경로를 재현했다. 1,500원 65,605,644원 → 1,000원 60,226,298원, 감소 5,379,346원. 같은 기준매출을 50:50으로 나눈 이용시간 고정 계산은 54,671,370원이다. 최신 운영 수치나 실제 요금 변경 후 실적이 아니다.
- 별도 브라우저 조회의 송도점 기본 예측은 66,051,335원으로 보관 자료와 달랐다. 예시의 7,000만원 및 50:50 구성은 실제 송도점 구성이라고 단정하지 않는다.
- Claude 독립 검토의 횡단면 회귀와 동일 점포 가격 시나리오 구분은 채택했다. 기본 설정의 회귀/중앙값 0.8/0.2를 운영값으로 본 설명과 역산한 표준편차는 채택하지 않았다. 보관 설정은 1/0이다. 상품매출을 고정하면 상품 비중이 달라지므로 기존 고정 비중 기반 가동률 상한을 재적용하자는 제안도 채택하지 않았다.
- 이전 검토의 수동 동기화 스크립트 `candidateCode` 불일치도 수정했다. 원본 후보지 코드 우선 연결을 cron과 맞추고 기존 문서 ID는 유지한다.

검증: 일반 테스트 18파일 442개, 보관 자료 재현 테스트 1개, TypeScript, 변경 파일 ESLint, 프로덕션 빌드, diff 검사 통과. 로컬 검증 화면에서 송도점 선택 및 위 예시의 결과를 실제 입력으로 확인하고 화면 배치도 확인했다. 후보지 결과 화면은 자동 저장되므로 열지 않았다. 운영 배포와 실제 동기화는 수행하지 않았다.

후속: 주 예측에 요금의 직접 효과를 반영하려면 기준 이용량을 정하는 방식과 PC·먹거리 매출 분리, 과거 실적과 당시 적용 요금의 대응부터 정해야 한다. 현재 요금 하나를 과거 전체 매출에 붙여 학습하거나 요금 계수 하한을 임의로 높이는 방식으로 해결됐다고 보지 않는다.

## 재개 작업 — 계산 범위 검증

- 유한한 입력이어도 중간 곱셈과 결과가 Infinity가 될 수 있음을 재현했다. 요금 비율을 먼저 계산하고, 최종 금액이 안전한 원 단위 정수 범위를 넘으면 결과 대신 입력 안내를 표시한다.
- 같은 매우 큰 기준·변경요금의 비율은 정상 계산하며, 결과 오버플로와 안전 정수 범위 초과를 거부하는 테스트 3개를 추가했다. 일반 테스트 18파일 445개, 변경 파일 ESLint, 프로덕션 빌드·TypeScript 통과. 이번 재개에서는 브라우저 검증을 다시 수행하지 않았다.
- 코드상 `ExistingStoreMonthlySales`에는 월별 `pcSales`, `productSales`가 이미 있다. 다만 당시 요금 필드는 없고 `ExistingStore.hourlyRate`는 현재 기본정보 값이다. 실제 월별 값의 충실도는 이번 코드 검토로 확인한 것이 아니다.
- 다음 모델 작업의 최소 자료는 점포·월별 PC매출, 먹거리 매출, 그 기간의 실효 시간당요금 또는 실제 유료 이용시간이다. 요금표 가격과 실효 단가는 구분해야 한다. 이 연결 자료를 확보한 다음 이용량을 학습하는 방식과 기존 총매출 회귀를 분리 검증한다.

## Claude 독립 검토 대조

- Claude가 확인한 소수 금액의 구성 합계 불일치를 재현하고 수정했다. 항목별 원 단위 반올림 후 총액과 증감을 계산한다. 유지·인하·인상 테스트를 추가해 일반 테스트 18파일 448개 통과.
- 오버플로 지적은 Codex가 병행 수정한 내용과 일치한다. 다만 Claude는 수정 전 함수와 수정 후 테스트를 읽었으므로 “커밋된 테스트가 실패한다”는 결론은 채택하지 않았다. 실제 실행 결과를 검증 근거로 사용한다.
- `_tariffReview.test.ts`는 미추적 로컬 보관 자료 분석이며 CI 회귀 테스트가 아니다. 앞의 “보관 자료 재현 테스트 1개”는 당시 로컬 분석 실행 성공을 뜻하고, 계산 수치가 자동 단정되었다는 의미가 아니다. 해당 파일은 이번 변경 및 배포 대상에 포함하지 않는다. TypeScript의 `!`는 런타임 검사가 아니므로 `toBeDefined()`가 절대 실패하지 않는다는 Claude 설명도 채택하지 않았다.
- 운영 조회와 보관 자료의 송도점 수치 차이는 입력 시점이 다른 비교이며, 이번 검토로 원인을 특정하지 않았다. 주 예측 변경의 정확도 근거로 사용하지 않는다.

## 2026-09-08 재개 점검 — 분리 모형 적용 판단

- accuracy-release의 미커밋 초안을 보존한 상태에서 일반 테스트 18파일 448개 및 TypeScript 검사를 재실행해 통과했다.
- `_priceModelReview.test.ts`의 보관 자료 분석도 실행했다. 자료 시점은 2026-09-08T00:05:10.035Z이며 운영 재조회는 하지 않았다.
- 38곳 기준 기존 경로는 MAPE 10.43%, ±10% 19/38, ±20% 34/38. PC·먹거리 분리 실험은 MAPE 11.46%, ±10% 20/38, ±20% 30/38이다. 최악 과소는 -21.42%에서 -23.19%로 악화되고 최악 과대는 +28.08%에서 +24.92%로 줄었다. 전반적 정확도 개선 기준을 충족하지 않는다.
- 이 분석은 자체 산식으로 계산하며 미추적 usageRevenue.ts 구현을 직접 호출하지 않는다. 분석 테스트의 성공은 해당 구현의 회귀 검증 완료를 뜻하지 않는다.
- evaluate.ts 초안은 trainingSales 전달 여부로 새 모형을 선택하지만 현재 후보지 호출부에는 전달이 없고 검증 화면도 기존 산식을 사용한다. 웹 호출부에서 전달한다는 주석과 실제 연결 상태가 다르다.
- usageRevenue.ts는 과거 PC매출을 현재 hourlyRate로 나누어 이용시간을 추정한다. 당시 실효요금과의 대응이 확인되지 않아 실제 이용시간 학습이라고 확정할 수 없다.
- 다음 구현 전 해결할 사항은 과거 요금/이용시간 자료의 정의, 새 구현 자체에 대한 회귀 검증, 후보지와 검증 경로의 일치다. 이번 점검에서는 모형 활성화·운영 배포·자료 쓰기를 하지 않았다.
