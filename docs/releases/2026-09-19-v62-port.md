## 0. 판정 기준 — MAPE는 근거가 아니라 대가다

사용자(2026-09-19): *"v62라고 mape 위주로 진행하는 게 아니라, 근거가 명확한, 이런 값이라면
적중률이 떨어져도 적용해야지."*

그래서 근거를 **종류**로 갈랐다.

```
  [사실 문제]  운영 값이 사실과 어긋난다        -> 적중률과 무관하게 고친다
  [통계 근거]  관문(위약·대조군·LOO)을 통과했다  -> 대가를 보고 정한다
  [판단]      뜻으로 고른 값이다              -> 사실 교정과 같이 넘기지 않는다
  [근거 약함]  실험실 안에서만 뜻이 있다        -> 안 건드린다
```

| 항목 | 종류 | 상태 |
|---|---|---|
| 사양 **변환표**(GPU·CPU 성능지수) | 사실 | ✅ 1단계 (2026-09-19 낮) |
| **존구성** 잣대 교체 | 사실 | ✅ 2단계 (이 문서) |
| **QSC 관리 수준** 피처 추가 | 통계 | ✅ 3단계 (이 문서) |
| 사양 **비중** 0.4/0.25→0.5/0.15 | **판단** | ⛔ 안 함 |
| 사양 RAM·모니터 변환 | 판단 성격 | ⛔ 안 함 |
| 중심도·교과서식 예측·특수수요 배수 | 근거 약함 | ⛔ 안 함 |

## 1. 결과 — 적중률은 어디로 갔나

**리브원아웃 n=38 정식검증군** (`_liveCheck.test.ts`, 2026-09-19 밤 측정)

```

  1단계까지          9.22%    8.44%    24곳 63%  36곳 95%
  +2단계 존구성     10.31%    8.65%    22곳 58%  35곳 92%
  +3단계 QSC         8.96%    8.11%    24곳 63%  35곳 92%   <- 지금
```

읽는 법:

- **존구성만 보면 나빠진다**(MAPE +1.09%p). 예상한 대가다 — 틀린 값을 고쳤으니 그렇다.
- **QSC가 그걸 되돌리고 더 간다.** 최종적으로 1단계 시점보다 MAPE·중앙값이 좋아졌다.
- 잃은 건 **±20% 한 곳**뿐이다(36곳 → 35곳).
- ⚠️ **"둘을 합쳤더니 좋아졌으니 존구성이 옳았다"가 아니다.** 존구성은 숫자와 무관하게
  사실 문제라서 고쳤고, QSC는 별개의 근거로 들어갔다. 둘을 섞어서 서로를 정당화하면
  안 된다.

## 2. 2단계 — 존구성을 물리 좌석으로 센다

### 근거 (사실 문제)

경쟁점 조사표에 **VIP존·프렌즈존·퍼스트클래스존 칸이 228건 전부 0건**이다. 우리 브랜드
용어라 조사자가 경쟁점의 같은 실체(파티션 1인석 등)를 보고도 그 칸에 안 넣는다. 게다가
자사엔 "일반 2인석" 칸이 아예 없어서 우리 2인석은 전부 커플존으로 계상된다.

운영은 **존 이름 종류 수**로 다양성을 셌으므로, 같은 가게를 우리 말로 적으면 점수가
올라가고 조사자 말로 적으면 내려갔다. **경쟁점이 아무리 좋아도 자사를 못 따라잡는다.**

### 바뀐 것

```
  존다양성 = 룸 종류 수만 (1인룸·2인룸·팀룸)      <- 양쪽 다 조사되는 물리 사실
  특화좌석 = 이름과 무관하게 실재하는 좌석 전부   <- VIP존은 1인석, 프렌즈존은 좌석 수
  퍼스트클래스존 = 팀룸과 같은 칸 · 좌석은 룸 1개 = 11석
  일반2인석 다양성 +0.5 가산 폐지                <- 이름표 비대칭의 다른 얼굴이었다
  비중 = 다양성 0.3 · 수용력 0.7                 <- 7:3에서 뒤집힘
```

비중을 뒤집은 건 **판단**이다(룸만 세면 사실상 "팀룸 있나 없나"의 이진이 된다).
⚠️ MAPE로 고른 값이 아니다 — 존구성에는 매장별 순서 정보가 거의 없다는 게
`_zoneComposition.test.ts`의 결론이라 여기서 MAPE는 채택 근거가 못 된다.

### 측정으로 확인된 것 (조사된 경쟁점 194곳 · 중앙값)

```
  [옛 잣대]  다양성 자사 3.50 / 경쟁 1.00  차이 2.50    수용력 3.00 / 1.00  차이 2.00
  [새 잣대]  다양성 자사 2.00 / 경쟁 1.00  차이 1.00    수용력 4.00 / 1.00  차이 3.00
```

**이름표 우위가 2.50 → 1.00으로 걷혔다.** 수용력 차이가 느는 건 VIP존이 1인석으로,
프렌즈존이 좌석으로 제대로 세어져서다 — 실재하는 좌석이라 맞는 방향이다.

⚠️ 총점은 3.35 → 3.40으로 비슷하다(둘이 상쇄). **승률로 보면 안 보이고 분해해야 보인다.**

### 코드

- 잣대의 **원본이 `calc.ts`로 옮겨왔다.** `labZoneComposition.ts`는 실험실 쪽 이름만 남긴
  껍데기가 됐다(두 벌이면 조용히 갈라진다 — `labSpecScore.ts`에서 실제로 그랬다).
- 미조사 경쟁점 기본값은 원래부터 양쪽 다 1.0이었다. 상수 하나로 합쳤다.
- `calc.test.ts`에 **잣대 교체의 이유 자체를 잠그는 시험**을 넣었다 —
  *"같은 실체를 우리 이름표로 적든 조사자 말로 적든 점수가 같다"*.

## 3. 3단계 — QSC 관리 수준을 학습 피처로

### 근거 (통계)

지금까지 자사 관리 점수는 **38곳 전부 4.00 상수**였다. 칸은 있는데 아무것도 재고 있지
않았다는 뜻이다. 그래서 관리가 낮은 매장을 과대예측했다 — 구미산동점 QSC 73.9로 최저,
오차 +17.9% → **+3.9%**.

```
  탄력도 0.84 (QSC 1% ↑ -> 매출 0.84% ↑) · 설명 분산 18.1%
  위약군 5개(실험실이 기각한 항목) 전부 실패 · 난수 칸 40회 전부 미달
```

### 값과 채우는 규칙

```
  피처 = log(QSC / 92.6)      92.6은 2026-09-19 가맹점 기하평균
  점검 기록이 없는 매장·후보지 = 학습표본 기하평균 (= 표준화 뒤 0 = 중립)
```

⚠️ **92.6은 읽기 좋으라고 두는 기준점일 뿐 모형에 영향이 없다**(표준화가 중심을 다시
잡는다). 빈 곳을 메울 때는 이 상수가 아니라 **그 코호트의 실제 기하평균**을 쓴다 —
상수로 박으면 표본이 늘어도 안 따라 움직인다.

채우는 자리는 `calc.ts`의 `qscFillerFor` **한 곳**이다. 화면마다 각자 평균을 내면 같은
매장이 검증 화면과 후보지 화면에서 다른 관리 수준을 받는다.

### 데이터 경로 — 운영 컬렉션을 새로 만들었다

```
  운영:   storeEvalQscScores      <- V62가 읽는다 (신설)
  실험실: storeEvalLabQscScores   <- 그대로
```

`writeQscScoresToFirestore.mjs`가 **한 번에 둘 다 채우고**, 인자 없이 돌리면 두 컬렉션이
갈라졌는지 찍어 준다. `firestore.rules`에 운영 쪽 규칙을 추가했다(권한은 실험실과 동일).

왜 실험실 것을 그냥 안 읽나: 2026-09-16에 "실험실에서 고친 값이 운영을 움직이면 안 된다"고
컬렉션을 갈라놨다. 그런데 **QSC는 실험실이 고치는 값이 아니라 본사가 매긴 점검 기록**이다 —
월매출과 같은 성격이라 원본이 운영 쪽에 있는 게 맞다.

### 안전장치

- 컬렉션이 비어 있거나 읽기에 실패하면 **QSC 칸이 아예 안 붙고 2026-09-19 이전과 똑같이
  동작한다.** 깨지지 않는다. 이걸 시험으로 잠가 뒀다.
- 학습·예측이 **같은 칸 수**여야 한다(섞이면 학습이 null이 된다). 피처·라벨·하한선 배열이
  항상 같이 늘어나는 것도 시험으로 잠갔다.

## 4. ⚠️ 밟은 함정 (2026-09-19)

1. **"후보지는 한 톨도 안 바뀐다"는 거짓이다.** 칸을 더하면 나머지 계수가 다시 학습된다.
   실제로 재니 세 변경 합쳐 −5.5% ~ +1.0%였다.
2. **상수 칸으로 후보지를 흉내내면 안 된다.** 전 매장에 같은 값을 넣으면 분산 0이라
   표준화에서 전부 0이 되고 학습이 기준선과 같아진다. 올바른 흉내는 **실제 값으로 학습 →
   평균으로 예측**이다.
3. **승률로 편향을 판정하면 안 된다.** 존구성에서 자사 승률 98→100%만 보고 "안 고쳐진다"고
   오판했다. **다양성·수용력으로 분해해야** 이름표 우위가 걷힌 게 보인다.
4. **사실 교정과 판단을 섞어 재면 안 된다.** "사양 교체는 나빠진다"고 적었는데 비중 변경까지
   같이 넘겨서였다. 갈라내니 달랐다.
5. **숫자를 인용할 때 무엇까지 포함한 값인지 확인할 것.** "변환표만 9.06%"라고 적었는데
   그건 RAM·모니터까지 포함한 값이었고, GPU+CPU만은 9.22%였다.
6. **하네스도 운영과 같은 모양으로 고쳐야 한다.** QSC를 운영에만 넣고 `_liveCheck`의 계수
   진단 블록을 안 고쳤더니, 거기서만 피처 길이가 어긋나 모형이 통째로 null이 됐다.
   같은 이유로 `storedAccuracyParity`에도 QSC를 실었다 — 안 그러면 그 시험만 화면과 다른
   숫자로 통과/실패한다.
