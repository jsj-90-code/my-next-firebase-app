## 0. 판정 기준 — MAPE는 근거가 아니라 대가다

사용자(2026-09-19): *"v62라고 mape 위주로 진행하는 게 아니라, 근거가 명확한, 이런 값이라면
적중률이 떨어져도 적용해야지."*

그래서 근거를 **종류**로 갈랐다.

```
  [사실 문제]  운영 값이 사실과 어긋난다        -> 적중률과 무관하게 고친다
  [통계 근거]  관문(위약·대조군·LOO)을 통과했다  -> 대가를 보고 정한다
  [판단]      뜻으로 고른 값이다              -> 사실 교정과 같이 넘기지 않는다
  [근거 약함]  실험실 안에서만 뜻이 있다        -> 안 건드린다
```

| 항목 | 종류 | 상태 |
|---|---|---|
| 사양 **변환표**(GPU·CPU 성능지수) | 사실 | ✅ 1단계 (2026-09-19 낮) |
| **존구성** 잣대 교체 | 사실 | ✅ 2단계 (이 문서) |
| **QSC 관리 수준** 피처 추가 | 통계 | ✅ 3단계 (이 문서) |
| **모니터** 잣대 교체 | 사실(변별력·파싱) + **판단**(가산값) | ✅ 5단계 (이 문서 6절) |
| 사양 **비중** 0.4/0.25→0.5/0.15 | **판단** | ⛔ 안 함 |
| 사양 RAM 격차 0.5 | 아직 못 잼 | ⛔ 안 함 (6절 끝 참고) |
| 중심도·교과서식 예측·특수수요 배수 | 근거 약함 | ⛔ 안 함 |

## 1. 결과 — 적중률은 어디로 갔나

**리브원아웃 n=38 정식검증군** (`_liveCheck.test.ts`, 2026-09-19 밤 측정)

```
                     MAPE     중앙값    ±10%      ±20%
  1단계까지          9.22%    8.44%    24곳 63%  36곳 95%
  +2단계 존구성     10.31%    8.65%    22곳 58%  35곳 92%
  +3단계 QSC         8.96%    8.11%    24곳 63%  35곳 92%
  +5단계 모니터      8.92%    7.67%    24곳 63%  34곳 89%   <- 지금
```

읽는 법:

- **존구성만 보면 나빠진다**(MAPE +1.09%p). 예상한 대가다 — 틀린 값을 고쳤으니 그렇다.
- **QSC가 그걸 되돌리고 더 간다.** 최종적으로 1단계 시점보다 MAPE·중앙값이 좋아졌다.
- 잃은 건 **±20% 한 곳**뿐이다(36곳 → 35곳).
- ⚠️ **"둘을 합쳤더니 좋아졌으니 존구성이 옳았다"가 아니다.** 존구성은 숫자와 무관하게
  사실 문제라서 고쳤고, QSC는 별개의 근거로 들어갔다. 둘을 섞어서 서로를 정당화하면
  안 된다.

### 계수 고착 검사 (2026-09-10 확립한 관문)

```
  피처            하한선   PC(이용시간)  먹거리   PC구속  먹거리구속
  IP당수요         0.030      0.0300    0.0300     예        예
  경쟁력점수        0.000      0.0207    0.0805     -         -
  경쟁력x격차       0.090      0.0900    0.0900     예        예
  배후수요더미      0.050      0.0500    0.0500     예        예
  가시성           0.050      0.0669    0.0524     -         -
  QSC관리수준       0.000      0.0485    0.0369     -         -   <- 새 칸
```

**QSC 칸은 하한선에 안 붙었다.** 사람이 정한 값이 아니라 자료가 정한 값이라는 뜻이다.

### 후보지는 얼마나 움직였나

저장된 결과(2026-09-17) 대비, **네 변경을 합친** 값이다(`storedAccuracyParity`).

```
  N001 신중동     -1.32%     N010 창원상남   -4.76%
  N002 춘천퇴계   -1.22%     N011 마산산호   -4.65%
  N003 호구포역   -2.44%     N012 산본       -4.09%
  N004 하안금당   -4.31%     N013 김포풍무   -4.66%
  N005 울산삼산   -5.25%     N014 영월       -4.36%

                             N016 오송       -0.74%
```

**전부 내려갔고 폭은 −0.7% ~ −5.3%다.** 대부분은 **존구성 교정 몫**이다(자사 존구성이 이름표
가점을 잃었다). QSC·모니터는 각각 ±1%p 안쪽이다. **등급이 뒤집힐 크기는 아니지만 "안 바뀐다"도
아니다** — 4절 함정 참고.

⚠️ **방향이 한쪽인 게 우연은 아니다.** 존구성 이름표를 걷어내면 자사 경쟁력이 내려가고,
그러면 후보지 예상매출도 같이 내려간다. 그동안 **후보지를 조금씩 후하게 보고 있었다**는 뜻이다.

## 2. 2단계 — 존구성을 물리 좌석으로 센다

### 근거 (사실 문제)

경쟁점 조사표에 **VIP존·프렌즈존·퍼스트클래스존 칸이 228건 전부 0건**이다. 우리 브랜드
용어라 조사자가 경쟁점의 같은 실체(파티션 1인석 등)를 보고도 그 칸에 안 넣는다. 게다가
자사엔 "일반 2인석" 칸이 아예 없어서 우리 2인석은 전부 커플존으로 계상된다.

운영은 **존 이름 종류 수**로 다양성을 셌으므로, 같은 가게를 우리 말로 적으면 점수가
올라가고 조사자 말로 적으면 내려갔다. **경쟁점이 아무리 좋아도 자사를 못 따라잡는다.**

### 바뀐 것

```
  존다양성 = 룸 종류 수만 (1인룸·2인룸·팀룸)      <- 양쪽 다 조사되는 물리 사실
  특화좌석 = 이름과 무관하게 실재하는 좌석 전부   <- VIP존은 1인석, 프렌즈존은 좌석 수
  퍼스트클래스존 = 팀룸과 같은 칸 · 좌석은 룸 1개 = 11석
  일반2인석 다양성 +0.5 가산 폐지                <- 이름표 비대칭의 다른 얼굴이었다
  비중 = 다양성 0.3 · 수용력 0.7                 <- 7:3에서 뒤집힘
```

비중을 뒤집은 건 **판단**이다(룸만 세면 사실상 "팀룸 있나 없나"의 이진이 된다).
⚠️ MAPE로 고른 값이 아니다 — 존구성에는 매장별 순서 정보가 거의 없다는 게
`_zoneComposition.test.ts`의 결론이라 여기서 MAPE는 채택 근거가 못 된다.

### 측정으로 확인된 것 (조사된 경쟁점 194곳 · 중앙값)

```
  [옛 잣대]  다양성 자사 3.50 / 경쟁 1.00  차이 2.50    수용력 3.00 / 1.00  차이 2.00
  [새 잣대]  다양성 자사 2.00 / 경쟁 1.00  차이 1.00    수용력 4.00 / 1.00  차이 3.00
```

**이름표 우위가 2.50 → 1.00으로 걷혔다.** 수용력 차이가 느는 건 VIP존이 1인석으로,
프렌즈존이 좌석으로 제대로 세어져서다 — 실재하는 좌석이라 맞는 방향이다.

⚠️ 총점은 3.35 → 3.40으로 비슷하다(둘이 상쇄). **승률로 보면 안 보이고 분해해야 보인다.**

### 코드

- 잣대의 **원본이 `calc.ts`로 옮겨왔다.** `labZoneComposition.ts`는 실험실 쪽 이름만 남긴
  껍데기가 됐다(두 벌이면 조용히 갈라진다 — `labSpecScore.ts`에서 실제로 그랬다).
- 미조사 경쟁점 기본값은 원래부터 양쪽 다 1.0이었다. 상수 하나로 합쳤다.
- `calc.test.ts`에 **잣대 교체의 이유 자체를 잠그는 시험**을 넣었다 —
  *"같은 실체를 우리 이름표로 적든 조사자 말로 적든 점수가 같다"*.

## 3. 3단계 — QSC 관리 수준을 학습 피처로

### 근거 (통계)

지금까지 자사 관리 점수는 **38곳 전부 4.00 상수**였다. 칸은 있는데 아무것도 재고 있지
않았다는 뜻이다. 그래서 관리가 낮은 매장을 과대예측했다 — 구미산동점 QSC 73.9로 최저,
오차 +17.9% → **+3.9%**.

```
  탄력도 0.84 (QSC 1% ↑ -> 매출 0.84% ↑) · 설명 분산 18.1%
  위약군 5개(실험실이 기각한 항목) 전부 실패 · 난수 칸 40회 전부 미달
```

### 값과 채우는 규칙

```
  피처 = log(QSC / 92.6)      92.6은 2026-09-19 가맹점 기하평균
  점검 기록이 없는 매장·후보지 = 학습표본 기하평균 (= 표준화 뒤 0 = 중립)
```

⚠️ **92.6은 읽기 좋으라고 두는 기준점일 뿐 모형에 영향이 없다**(표준화가 중심을 다시
잡는다). 빈 곳을 메울 때는 이 상수가 아니라 **그 코호트의 실제 기하평균**을 쓴다 —
상수로 박으면 표본이 늘어도 안 따라 움직인다.

채우는 자리는 `calc.ts`의 `qscFillerFor` **한 곳**이다. 화면마다 각자 평균을 내면 같은
매장이 검증 화면과 후보지 화면에서 다른 관리 수준을 받는다.

### 데이터 경로 — 운영 컬렉션을 새로 만들었다

```
  운영:   storeEvalQscScores      <- V62가 읽는다 (신설)
  실험실: storeEvalLabQscScores   <- 그대로
```

`writeQscScoresToFirestore.mjs`가 **한 번에 둘 다 채우고**, 인자 없이 돌리면 두 컬렉션이
갈라졌는지 찍어 준다. `firestore.rules`에 운영 쪽 규칙을 추가했다(권한은 실험실과 동일).

왜 실험실 것을 그냥 안 읽나: 2026-09-16에 "실험실에서 고친 값이 운영을 움직이면 안 된다"고
컬렉션을 갈라놨다. 그런데 **QSC는 실험실이 고치는 값이 아니라 본사가 매긴 점검 기록**이다 —
월매출과 같은 성격이라 원본이 운영 쪽에 있는 게 맞다.

### 안전장치

- 컬렉션이 비어 있거나 읽기에 실패하면 **QSC 칸이 아예 안 붙고 2026-09-19 이전과 똑같이
  동작한다.** 깨지지 않는다. 이걸 시험으로 잠가 뒀다.
- 학습·예측이 **같은 칸 수**여야 한다(섞이면 학습이 null이 된다). 피처·라벨·하한선 배열이
  항상 같이 늘어나는 것도 시험으로 잠갔다.

## 4. ⚠️ 밟은 함정 (2026-09-19)

1. **"후보지는 한 톨도 안 바뀐다"는 거짓이다.** 칸을 더하면 나머지 계수가 다시 학습된다.
   실제로 재니 세 변경 합쳐 −5.5% ~ +1.0%였다.
2. **상수 칸으로 후보지를 흉내내면 안 된다.** 전 매장에 같은 값을 넣으면 분산 0이라
   표준화에서 전부 0이 되고 학습이 기준선과 같아진다. 올바른 흉내는 **실제 값으로 학습 →
   평균으로 예측**이다.
3. **승률로 편향을 판정하면 안 된다.** 존구성에서 자사 승률 98→100%만 보고 "안 고쳐진다"고
   오판했다. **다양성·수용력으로 분해해야** 이름표 우위가 걷힌 게 보인다.
4. **사실 교정과 판단을 섞어 재면 안 된다.** "사양 교체는 나빠진다"고 적었는데 비중 변경까지
   같이 넘겨서였다. 갈라내니 달랐다.
5. **숫자를 인용할 때 무엇까지 포함한 값인지 확인할 것.** "변환표만 9.06%"라고 적었는데
   그건 RAM·모니터까지 포함한 값이었고, GPU+CPU만은 9.22%였다.
6. **하네스도 운영과 같은 모양으로 고쳐야 한다.** QSC를 운영에만 넣고 `_liveCheck`의 계수
   진단 블록을 안 고쳤더니, 거기서만 피처 길이가 어긋나 모형이 통째로 null이 됐다.
   같은 이유로 `storedAccuracyParity`에도 QSC를 실었다 — 안 그러면 그 시험만 화면과 다른
   숫자로 통과/실패한다.

## 6. 5단계 — 모니터 잣대 교체 (사용자 요청으로 추가)

사용자(2026-09-19, 위 3단계까지 끝낸 뒤): *"모니터가산까지 들어가야할거같은데? 기존값은
변별력이 좀 떨어질텐데"*

### 변별력은 재보니 맞는 말이었다 (사실)

자사+경쟁 196칸을 채점해 비교했다.

```
              고유값   상위 3개 동점 덩어리   자사 38곳 표준편차
  옛 구간표    21개    118칸 (60%)          0.15  <- 사실상 상수
  새 연속눈금  61개     63칸 (32%)          0.06
```

옛 구간표는 **3.50점에 49곳 · 3.00점에 35곳 · 3.85점에 34곳**이 뭉쳐 있었다.

### ⚠️ 내가 처음 지목한 건 헛다리였다

운영 코드 첫 줄이 `if (/4K|UHD|OLED/) return 5` — **Hz를 아예 안 보고 만점**이라
OLED 60Hz와 OLED 240Hz가 똑같이 5.00이었다. 논리적으로는 버그가 맞다. 그런데
**이것만 고쳐 재니 변화가 정확히 0.0000이었다.** 실데이터 5건이 전부 240Hz 이상이라
Hz를 봐도 어차피 만점이었다. **잠복 버그지 지금 손해가 아니다.**

교훈: "논리적으로 틀렸다"와 "지금 손해를 보고 있다"는 다르다. 갈라서 재야 안다.

### 진짜 영향을 준 건 파싱 오류였다 (사실)

운영은 칸을 **콤마로만** 쪼갰는데 조사 자료는 모델을 **줄바꿈**으로 나열한다. 그래서
여러 모델이 한 덩어리가 되고 Hz를 **먼저 평균낸 뒤** 한 번 채점했다.

```
  "Geekstar QHD 144Hz / AMH FHD 60Hz / 삼성 144Hz"
    옛: Hz 평균 116 -> 1.50점      새: 낱개 3.20/1.29/3.00 -> 2.50점
```

이걸 **단독으로** 재면 MAPE 8.96 → 8.92% · 중앙 8.11 → 8.06%이고, **자사 경쟁력점수가
23곳 내려가고 6곳만 올라간다**(평균 −0.0019). 우리에게 **불리한** 방향이라 자기기만
위험이 없다.

### 가산값 일곱 개는 판단이다 (⚠️ 이게 제일 중요하다)

```
  OLED 1.5 · 4K 1.0 · QHD 0.7336 · ZOWIE 0.6 · BenQ 0.4 · 게이밍브랜드 0.4 · 울트라와이드 0.3
```

**검증할 외부 기준이 없다.** GPU 성능지수는 공개 벤치마크가 있어서 "RTX 3060 Ti > RTX 4060"이
참·거짓으로 갈렸지만 모니터는 아니다. `labSpecScore.ts`가 스스로 *"가산 일곱 개가 전부 [감각]
계수다"*라고 적어 뒀다.

크기 순서는 사용자가 원가·프리미엄 등급으로 정했다(2026-09-18). QHD 0.7336만은 사용자가 준
등가점(*"32인치 FHD 240Hz와 27인치 QHD 165Hz는 두개사실 비슷함"*)에서 `ln(165/240)/0.5108`로
역산한 값이라 **앵커가 있는** 감각이다.

> 📌 **읽는 법: "맞는 값을 찾았다"가 아니라 "지금 손에 있는 최선의 추정치"다.**
> 나중에 외부 기준이 생기면 여기를 먼저 열 것. 지금 값이 틀렸다고 드러나도 놀랄 일이 아니다.

### 자기기만 검사 (통과)

```
  자사÷경쟁 모니터 점수 비율   1.12 -> 1.12  (불변)
```

절대값은 양쪽 다 오르지만(자사 3.76→4.10 · 경쟁 3.36→3.68) **모델이 쓰는 비율은 안 움직인다.**
존구성 이름표처럼 우리만 이득 보는 구조가 아니다.

가산 항목이 어느 쪽에 있는지도 셌다 — **OLED·4K는 자사 0건 / 경쟁 5건**으로 우리에게 **불리한**
방향이다. **울트라와이드만 자사 27 / 경쟁 3으로 쏠려 있어서** 존구성에서 걷어낸 "자사 전용
이름표"와 같은 모양인지 따로 쟀는데, **0으로 두든 0.3으로 두든 결과가 같았다**
(MAPE 8.923% vs 8.902% · ±10%·±20% 동일). 숫자를 못 만드는 가산이라 **작게 둔 채로 유지**한다 —
빼서 얻는 것도 없고, 울트라와이드는 경쟁점 조사표에도 적히는(실제로 3건 적혔다) 물리 사실이라
VIP존 같은 이름표 함정과는 성격이 다르다.

### 같이 넘어온 것 — 듀얼모니터 보조화면 제외

보조 화면은 10인치 60Hz처럼 작은데, 그건 **모니터 품질이 나빠서가 아니라 보조 화면이라 작은
것**이다. 평균에 넣으면 그 매장이 부당하게 낮아진다(우리에게 유리한 왜곡). 그리고 **듀얼 좌석의
프리미엄은 존구성이 이미 센다**(`types.ts`: *1인석 = 칸막이·듀얼모니터만 있는 개방형 좌석*) —
여기서 또 주면 이중계산이라 **가점도 감점도 없이 빼기만** 한다.

### 코드

잣대의 **원본이 `calc.ts`로 왔다**(존구성과 같은 처리). `labSpecScore.ts`의
`labScoreFromMonitor*`는 껍데기가 됐고, 계수를 갈아끼우는 훑기 경로만 남았다.
옛 구간표는 `scoreFromMonitorStepTable`로 남겼다 — **비교 기준선 전용**이고, 실험실의
`useOperationalMonitor` 옵션이 "옛 잣대로 재면 어떤가"를 볼 때 쓴다(안 그러면 자기 자신과
비교하게 된다).

### 아직 안 넘긴 것 — RAM 격차 0.5

RAM만 남았다. 이건 판단이라기보다 **"아직 못 잰다"**에 가깝다 — 38곳 중 25곳(66%)의
평가창이 2025년 안에 끝나서 아이온2가 그 매출에 아예 없다. 표본의 평가창이 2026~2027로
넘어가면 다시 재야 한다.

📌 **사업 쪽 지적**: 32GB 비율이 **경쟁점 37% 대 자사 12%**다. **RAM은 우리가 밀린다.**
산식이 아니라 사양 정책 쪽 얘기라 여기서는 안 건드렸다.
