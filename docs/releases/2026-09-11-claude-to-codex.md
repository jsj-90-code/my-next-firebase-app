## 넘기는 것 ① — 월초 오전에 학습 구간이 한 달 어긋난다

`src/lib/storeEval/usageRevenue.ts:105`

```ts
const currentMonth = asOf.toISOString().slice(0, 7);
```

`toISOString()`은 UTC다. **한국시간 오전 0~9시는 UTC로 전날**이라, 매달 1일 오전 9시 이전에
실행하면 `currentMonth`가 한 달 전으로 잡힌다. 바로 아래 필터가

```ts
.filter(row => /^\d{4}-(0[1-9]|1[0-2])$/.test(row.yearMonth) && row.yearMonth < currentMonth)
```

이므로, 진행 중인 달 하나만 빼려던 것이 **직전 완료월까지 같이 빠진다.** 학습·검증 표본의
매출 구성이 한 달치 줄어든 채로 계산된다.

- 같은 패턴을 저장소 전수 확인했다. 실사용 코드에서 UTC 날짜를 쓰는 곳은 여기와
  `ResultTab.tsx`(내가 오늘 고쳤다), `spreadsheetPairs.ts`(엑셀 셀 라벨 변환이라 무해) 셋뿐이다.
- 화면 쪽 수정은 `format.ts`의 `formatDate`로 했다(로컬시간 기준). 다만 여기는 표시가 아니라
  **학습 구간 경계**라 같은 헬퍼를 그냥 쓰면 안 된다. `asOf`를 어느 시간대로 해석할지가
  먼저 정해져야 한다 — 운영 데이터가 KST 기준 월이라면 KST로 잘라야 맞다.
- 영향 범위는 실행 시각에 달려 있다. 매달 1일 09:00 KST 이전 실행에만 나타나므로
  지금까지의 측정값이 틀렸다는 뜻은 아니다. cron 동기화가 06:16 KST에 도는 것은 확인했다
  (`storeEvalSystemStatus/cronSync`) — **1일에 돌면 걸린다.**

내가 안 고친 이유: 시간대 해석을 바꾸면 학습 표본이 달라져 적중률 숫자가 움직인다.
그 판단은 산식 담당 몫이다.

## 넘기는 것 ② — 모형이 사실상 주관 인테리어 점수 하나로 움직인다

Codex가 08:32에 낸 `full-formula-audit-20260911.json`의 `sensitivitySummary`를 해석한 결과다.
숫자는 그쪽이 만든 것이고, 아래는 그것이 뜻하는 바다.

| 입력 변화 | 예측 반응(38곳) |
|---|---:|
| 상권수요 +10% | +0.50% |
| 경쟁점 IP +10% | −0.41% |
| **자사 경쟁력점수 +0.25** | **+11.7 ~ +13.9%** |

그리고 `ownScore` 실측 분포는 **3.31 ~ 4.10 (중앙 3.77)** 으로 폭이 0.79뿐이다.
즉 **관측된 전체 범위의 1/3만 움직여도 예상매출이 13% 뛴다.**

경쟁력점수의 구성비는 `settings.competitivenessWeights`가

```
인테리어 46.3% / 스펙 18.5% / 입지 18.5% / 먹거리 16.7%
```

이다. 인테리어 점수는 평가자가 매기는 주관 점수다. 정리하면
**예상매출의 최대 지렛대가 사람이 눈으로 매긴 인테리어 점수 하나**다.

왜 넘기는지:

- 이건 결함 보고가 아니라 **±10% 적중률이 53%에서 안 올라가는 구조적 이유의 후보**다.
  피처를 더 넣어도 비음수 릿지가 눌러버린다는 건 이미 확인됐는데(`backlog.md` "이미 해봤고
  안 되는 것"), 그 진짜 이유가 "설명력의 대부분을 저분산·주관 변수 하나가 이미 가져갔기
  때문"일 수 있다.
- 검증할 수 있는 형태로 만들면: **인테리어 점수를 고정하거나 평가자 편차를 제거했을 때
  잔차가 어떻게 변하는가.** 점수가 매출을 설명하는 게 아니라 매출을 본 뒤 점수를 맞춘
  것이라면(사후 합리화) 리브원아웃으로는 안 잡힌다.
- 사전 등록된 채택 조건(`backlog.md` §4)은 그대로 적용한다. 이건 계수를 건드리는 제안이 아니라
  **측정을 해보자는 제안**이다.
