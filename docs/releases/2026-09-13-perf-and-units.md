# 결과 탭 읽기 비용 측정(최적화 기각) + 금액 표기 통일 (2026-09-13)

사용자가 "완성도·품질·서비스를 높일 방안을 찾아 적용하라"고 위임한 뒤 첫 회차.

## 1. Firestore 읽기 비용 — 측정하고 **최적화는 기각**

"결과 탭이 매번 전체 모형을 재학습한다"는 지적을 재봤다. 도구: `.local-tools/measure-reads.mjs`.

### 결과 탭을 한 번 열면

| 건수 | 무엇 |
|---:|---|
| 41 | 기존점 전체 |
| 50 | 입지평가 전체 |
| 224 | 경쟁점 전체 |
| 480 | 월매출 12개월 구간 |
| 4 | 후보지·설정·정확도 등 |
| **799** | **합계** |

**그중 796건(99.6%)이 후보지와 무관한 공통 학습 데이터다.** 후보지를 바꿔 열어도 같은 값을
다시 읽는다. 9곳을 한 바퀴 돌면 약 7,191건.

### 그런데 최적화할 근거가 약하다

- **비용**: 9곳 한 바퀴에 **약 61원**(Blaze 읽기 10만건당 ~850원). 무시 가능하다.
- **왕복 횟수**: 문서 수는 많지만 쿼리는 적다. `listEvaluationSales`가 이미 `documentId in`으로
  필요한 것만 30개씩 묶어 4개 병렬로 읽는다(16청크 → 4라운드). 나머지는 컬렉션당 1쿼리다.
- **계산**: `evaluateCandidate` 한 번이 **5ms**다(2026-09-13 측정). 학습이 병목이 아니다.

세션 캐시를 넣으면 몇 백 ms를 아끼는 대신 **"옛 데이터로 계산"** 위험이 생긴다. 이 프로젝트는
"계산결과를 저장하지 않고 매번 재계산"이 원칙이라 그 방향과도 어긋난다.

**결론: 지금은 하지 않는다.** 다만 **실제 로딩 체감을 재본 적이 없다** — 사람이 화면을 열어
느리다고 느끼면 그때 다시 본다. 그 경우 후보지 간 이동에서만 쓰는 짧은 TTL 메모리 캐시가
첫 후보다(796건을 재사용).

## 2. 금액 표기가 한 화면에서 갈려 있었다 — 통일

결과 탭 안에서 `formatWon`(원) 25곳과 `formatManwon`(만원) 4곳이 섞여 있었다. 하필 **직접
비교되는 자리끼리** 단위가 달랐다.

```
V62 최종예상월매출   58,280,450원      <- 원
기존점 중앙값        6,378만원          <- 만원   (바로 아래 줄)
실측 정확도 범위     52,529,xxx원 ~ ... <- 원
2,000만원 기준매출   57,700,000원       <- 원
```

두 값을 견주려면 머릿속에서 자릿수를 옮겨야 했다. 만원 표기가 2026-09-13에 새로 들어오면서
생긴 불일치다(실제 평가기록이 만원을 쓰기 때문에 도입했다).

**고친 뒤:**

```
V62 최종예상월매출   약 5,800만원
                     58,280,450원      <- 작게 병기(정밀도 유지)
실측 정확도 범위     5,300만원 ~ 6,400만원
기존점 중앙값        6,378만원
2,000만원 기준매출   5,770만원 (57,700,000원 병기)
```

"예상이 선투자 기준을 살짝 넘고, 기존점 중앙값보다는 낮다"가 **한눈에 읽힌다.**

**정밀도를 버리지 않았다.** 큰 카드와 기준매출 카드는 원 단위를 `hint`로 작게 병기한다. 세부
계산값(V61 기본예측·보수/상한 밴드·요금·상품매출)은 원 단위 그대로 뒀다 — 비교 대상이 아니라
정확한 값을 확인하는 자리다.

## 안 한 것

- **접근성(aria/키보드)** — 전 화면 통틀어 10건뿐이라 후보로 봤지만, 이 도구는 사내 평가자
  한 명이 쓰는 내부 화면이라 우선순위가 낮다고 판단했다. 표 `scope`·`role="alert"` 정도는

- **실제 로딩 시간** — 브라우저 없이는 못 잰다. 사람이 체감을 말해주면 1번을 다시 연다.

# 2회차 — 테스트가 얇은 영역 측정 + 설정 병합 경계 못박기

## 측정: 어디가 실제로 얇은가

본문 120줄 이상인 모듈의 테스트 비율을 쟀다.

| 모듈 | 본문 | 테스트 | 비율 | 판단 |
|---|---:|---:|---:|---|
| types | 952 | 0 | 0% | 타입 선언뿐 — 대상 아님 |
| store | 746 | 0 | 0% | Firestore I/O 계층 — 모킹 없이는 어렵다 |
| cronSync | 620 | 58 | 9% | **착시** — 핵심 변환은 `scripts/lib/sheetParsers.mjs`에 있고 거기는 103줄 코드에 187줄 테스트(8개 중 7개 함수 커버)다 |
| settings | 236 | 24 | 10% | **진짜 얇았다 → 이번에 보강** |
| usageRevenue | 450 | 96 | 21% | 예측 경로. 산식 영역이라 이번엔 안 건드린다 |
| backup | 264 | 118 | 44% | `validateBackupPayload`는 11건으로 촘촘. 복원은 I/O |

## `mergeModelSettings` — 테스트 2건 → 8건

이 함수는 **옛 Firestore 문서 호환**을 담당한다. 필드가 추가될 때마다 지나가는 길인데 조용히
틀리면 잘못된 계수로 계산하고도 아무 신호가 없다. 경계 동작을 전부 못박았다.

- 저장값에 **없는 키(undefined)는 기본값 유지** ← 신규 필드 호환의 핵심
- **0·false를 기본값으로 되돌리지 않는다** (falsy라고 버리면 안 된다)
- `stored`가 null/undefined면 기본값 전체
- 중첩 객체는 준 키만 덮는다
- 기본값에 없는 낯선 키가 있어도 안 터진다
- 배열은 인덱스 병합하지 않고 통째로 교체(기존 테스트)

## null 위험을 의심했다가 — 경로가 닫혀 있음을 확인

`null`이 저장돼 있으면 **기본값으로 되돌리지 않고 null이 그대로 들어온다**(실측 확인). 그러면
`v62MaxUtilizationRate: null` 같은 상태에서 계산이 깨진다. 위험해 보여 경로를 전부 뒤졌다.

| 경로 | 결과 |
|---|---|
| 설정 화면 | **닫힘** — 빈 칸을 0으로 바꾸고(`value === "" ? 0 : Number(...)`), 표시도 `Number.isFinite(value) ? value : 0`, 저장 전 `modelSettingsValidationErrors` |
| 옛 문서 호환 | **해당 없음** — 키가 아예 없는(undefined) 경우이고 기본값이 유지된다 |
| 백업 복원 | **닫힘** — `restoreFromBackup`이 `if (payload.modelSettings)`로 null을 건너뛴다 |
| cronSync | **해당 없음** — 설정 문서를 쓰지 않는다 |

**그래서 "null도 기본값으로" 규칙을 넣지 않았다.** 막아야 할 경로가 없는데 규칙을 늘리면
`updatedBy`처럼 null이 정상인 필드까지 건드리게 된다. 대신 현재 동작과 그 판단 근거를 테스트
주석에 적어뒀다 — 다음에 같은 의심이 들면 뒤지지 말고 그걸 보면 된다.
