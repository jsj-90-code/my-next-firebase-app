# 담당자 판단 매출 — 산식을 건드리지 않고 사람 판단을 나란히 기록 (2026-09-13, 집 PC)

## 무엇을 왜 했나

사용자가 남긴 말 한 줄에서 출발했다.

> "예측 매출액 조정을 못 하니까 그게 좀 굉장히 찝찝하구만"

지금 구조는 **입력 → 산식 → 표시**로 끝이다. 현장을 다녀와서 "이 자리는 산식보다 잘 나온다"는
감각이 생겨도 그걸 시스템에 남길 데가 없었다.

**그런데 예측값을 직접 고치게 만들면 안 된다.** 이 프로젝트의 적중률(MAPE 9.88%)은 "산식이
스스로 내놓은 예측"을 실제 매출과 대조해서 잰 값이다. 사람이 손댄 값으로 MAPE를 재면 사람이
맞춘 값을 사람이 채점하는 꼴이라 숫자 자체가 무의미해진다. 지금까지 여덟 가지 개선안을 검정해
여섯을 기각한 판단 근거가 전부 이 측정치 위에 서 있다.

그래서 **고치는 게 아니라 나란히 적는** 방식으로 만들었다.

| | 전 | 후 |
|---|---|---|
| V62 예상매출 | 화면 표시 | **그대로** (한 글자도 안 바뀜) |
| 담당자 판단 매출 | 없음 | 새 입력 (비워둬도 됨) |
| 판단 근거 | 없음 | 새 입력 (한 줄 메모) |
| 누가·언제 | — | 저장 시 자동 기록 |

## 진짜 목적은 따로 있다

현장 판단을 버리지 않는 것도 이득이지만, 핵심은 그게 아니다.

**개점 후 실제 매출이 나오면 "산식이 맞았나, 사람이 맞았나"를 데이터로 알 수 있다.**

사람이 계통적으로 더 맞는다면, 그 차이가 곧 산식이 놓치고 있는 것의 단서다. 지금 산식 개선은
학습 표본 38곳에서 짜낼 걸 다 짜내 **표본 45~50곳까지 대기** 상태인데(`docs/backlog.md`
B-1), 이건 그 병목을 우회해서 개선 단서를 모으는 별도 경로이기도 하다.

그래서 후보지 화면에만 입력칸을 만들고 끝내지 않고, **전환 시점 스냅샷까지 이어붙였다.**

### 산식은 한 줄도 안 건드렸다

`calc.ts`와 `evaluate.ts`는 **변경 없음**. 이건 주장이 아니라 테스트로 고정했다.

- `evaluate.test.ts` — 판단값을 9,900만원으로 넣어도 `evaluateCandidate` 결과 객체가
  `calculatedAt`을 빼고 완전히 동일한지 확인한다.
- `judgedRevenueIsolation.test.ts` — **`calc.ts`·`evaluate.ts` 소스에 `judged*` 라는 식별자가
  등장하는지 자체를 검사한다.** 동작 테스트만으로는 "판단값이 있으면 그걸 우선 쓴다" 같은 편의
  한 줄이 결과를 바꾸지 않는 경로로 들어올 때 놓칠 수 있어서, 이름이 나타나는 것 자체를 막았다.
  같은 파일이 반대 방향도 지킨다 — 전환 스냅샷에서 판단값 동결이 사라지면 깨진다.

이 격리를 푸는 변경(예: 판단값을 학습 피처로 쓰는 실험)을 하려거든 테스트를 지우기 전에
`docs/backlog.md`에 근거부터 남길 것. 적중률 측정 체계 전체가 여기 걸려 있다.

## 화면 동작

**후보지 → 최종결과 탭**, "V62 최종예상월매출" 카드 바로 아래.

- 금액·근거를 적고 "판단 저장"을 누르면 후보지 문서에 저장된다. 배지로 **"산식에 반영되지 않음"**
  을 항상 띄운다.
- 금액을 입력하면 **V62 대비 몇 % 높게/낮게 봤는지**를 즉시 보여준다.
- 저장 안 된 변경이 있으면 경고가 뜨고, 저장돼 있으면 언제·누가 적었는지 보인다.
- 둘 다 비우고 저장하면 판단을 지운 것으로 보고 시각·작성자도 함께 지운다.

**기존 가맹점 화면**에서는 판단을 적어둔 매장에 한해 "예측 vs 실제매출" 카드에 두 칸이 더
붙는다 — 담당자 판단매출, 그 오차율. 실제 매출이 입력돼 있으면 산식과 사람 중 어느 쪽이 더
가까웠는지 한 줄로 알려주되, **"한 곳 결과로는 어느 쪽이 낫다고 말할 수 없다"** 는 단서를 항상
같이 띄운다(표본 1건으로 결론 내리는 걸 막기 위해).

### 저장할 때 최신 문서를 다시 읽는 이유

결과 탭이 들고 있는 후보지 값은 "계산을 시작한 시점"의 스냅샷이다. `saveCandidate`는 문서
전체를 덮어쓰므로(`setDoc`), 그 스냅샷을 그대로 저장하면 그 사이 기본정보 탭에서 고친 값이
날아간다. 그래서 저장 직전에 `getCandidate`로 최신을 읽고 **판단값 네 칸만 갈아끼운다.**

## 확인하지 못한 것

- **실제 화면에서 저장을 눌러보지 않았다.** 구글 로그인이 필요해서 개발서버를 띄워둔 상태로
  사용자 확인을 남겨둔다. 저장 경로는 기존 `saveCandidate`(다른 탭이 이미 매일 쓰는 함수)를
  그대로 타므로 위험은 낮지만, 눈으로 본 적은 없다.
- **전환 스냅샷 동결은 실제로 전환을 돌려보지 않았다.** 정적 검사로만 고정돼 있다.

## 하위호환

기존 후보지 문서에는 이 네 필드가 없다(`undefined`). 읽는 쪽은 전부 `?? null`로 받고,
전환 스냅샷도 `c.judgedRevenue ?? null`로 읽는다. 마이그레이션은 필요 없다.

`cronSync`는 `merge: true`라 매일 도는 시트 동기화가 이 필드를 지우지 않는다. 07 시트는
2026-09-10에 삭제돼서 후보지는 Firestore 전용이기도 하다.
