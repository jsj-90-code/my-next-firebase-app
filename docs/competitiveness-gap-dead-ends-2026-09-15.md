# 경쟁력격차를 고치려던 네 가지 시도 — 전부 기각 (2026-09-15)

발단: 어제 짝 비교에서 "종합 경쟁력점수가 가동률을 설명하지 못한다"가 나왔다
(`share-elasticity-pair-test-2026-09-15.md`). 그래서 원인을 찾아 고치려 했고,
**네 가지 가설을 세워 전부 재봤고 전부 기각했다.**

결론부터: **산식·계수·설정값은 하나도 바꾸지 않았다. 바꿀 이유를 못 찾았다.**

| 가설 | 결과 |
|---|---|
| ① 입지 점수의 자(尺)가 어긋나 있다 | 세 안 모두 정확도 **악화** |
| ② 자사 인테리어가 평가 누락이다 | 개점 1년차만 측정하므로 **4.00이 맞는 값** |
| ③ 관리를 QSC 점검표로 채우면 된다 | **넣으면 안 된다** — 신규 후보지에선 모르는 값 |
| ④ 후보지 N011이 학습 범위 밖이라 위험하다 | 그 구간이 **가장 정확**하다 |

---

## 출발점 — 무엇이 이상해 보였나

```
자사 종합 경쟁력   3.68 (3.20~4.08)      <- 좁다
경쟁점 평균        2.60 (1.98~3.86)
차이              +1.08점

정식 38곳 경쟁력격차  1.000 ~ 1.810
경쟁점이 우위인 곳    0곳                 <- 열위 표본이 없다
```

열위 표본이 없으면 "경쟁력이 떨어지면 점유율이 얼마나 빠지나"를 학습할 재료가 없다.
그래서 자사 점수가 부풀려진 원인을 찾으려 했다.

원자료를 보니 자사 시설 점수가 전부 고정값이었다.

```
정식 38곳 — 서로 다른 값이 몇 가지인가
  인테리어   38/38곳   1가지 (전부 4.00)
  관리       38/38곳   1가지 (전부 4.00)
  먹거리     38/38곳   1가지 (전부 4.00)
  리뉴얼연도   0/38곳   없음
  개점일     38/38곳   35가지
경쟁점: 인테리어 2.55(1.0~4.5) / 관리 2.67(1.5~4.5) / 먹거리 2.58(1.5~3.5)
```

## ① 입지 — 세 안 모두 악화

자사와 경쟁점이 입지를 **다른 방법으로** 매긴다.

```
자사   computeOwnLocationScore       = 상권위치·동선x0.6 + 선점경쟁x0.25 + 접근가시성x0.15
경쟁점 computeLocationScoreFromFacts = 층수 + 엘리베이터
실측    자사 4.10 (3.20~4.85)  /  경쟁점 3.82 (1.00~5.00)
```

정식 38곳의 실제 평가값을 두 자로 각각 재보면 차이가 분명하다.

```
코드 함수(경쟁점에 쓰는 자)와 일치   14/38곳  37%
평가자가 실제로 쓴 자와 일치         35/38곳  92%
```

| 매장 | 층 | 실제 평가값 | 경쟁점용 자로 재면 |
|---|---|---:|---:|
| 시흥능곡점 | 6층+엘베 | 2 | 1 |
| 안산선부점 | 5층+엘베 | 3 | 2 |
| 청주터미널점 | 2층+엘베 | 4 | 5 |
| 양주덕정점 | 2층+엘베 | 4 | 5 |

### 세 안을 같은 검증 경로로 잰 결과

| 안 | 내용 | MAPE | 중앙값 | ±10% | ±20% | 최악 |
|---|---|---:|---:|---:|---:|---:|
| **A** | **현행 유지** | **9.67%** | **8.90%** | 20/38 | 34/38 | 23.52% |
| B | 자사도 층수 자로 통일 | 11.54% | 11.61% | 17/38 | 35/38 | 28.34% |
| C | 경쟁력점수에서 입지 제거 | 10.76% | 9.92% | 19/38 | 34/38 | 22.58% |

열위 표본(격차<1)은 **A·B·C 전부 0곳**이라, 자를 맞춰도 원래 목적을 달성하지 못한다.

**해석(가설, 미검증):** 평가자가 매긴 값에는 층수 말고도 간판·코너·보행 노출이 들어가 있다.
이름만 같고 재는 대상이 다르므로, 억지로 맞추면 정보를 버리게 된다.

→ **현행 유지. 자가 다른 것은 의도된 상태로 둔다.**

하네스: `src/lib/storeEval/_locationYardstick.test.ts` (로컬 전용)

## ② 인테리어 — 개점 1년차라 노후도가 상수다

가설: `computeFreshnessFromYear`(리뉴얼연도 우선, 없으면 개점일)로 채우면 변별력이 생긴다.
이 함수는 2026-08-30 "경쟁력 평가 기준 최종본 §7"로 만들어졌는데 **계산 경로에 연결된 적이 없다**
(`calc.test.ts`에서만 호출된다).

기각 사유 — 사용자 지적: *"오픈 후 1년간의 데이터로만 해서 노후도는 평가대상이 아닐 텐데."*

`evaluationSalesPeriod.evaluationMonths()`는 **개점 다음 달부터 정확히 12개월**만 쓴다.

```
시흥능곡점   개점 2023-04  ->  측정 2023-05 ~ 2024-04
안산선부점   개점 2023-07  ->  측정 2023-08 ~ 2024-07
하남덕풍점   개점 2023-08  ->  측정 2023-09 ~ 2024-08
```

38곳 전부 "개점 1년차"다. 최신성으로 채우면 이렇게 된다.

```
5.0점  15곳
4.5점  12곳
4.0점  11곳
-> 전부 현행 4.0 이상. 격차가 더 벌어질 뿐이다.
```

**인테리어 4.00 고정은 측정 실패가 아니다.** 측정 구간에 실제로 전부 새 매장이고,
노후한 경쟁점보다 인테리어가 나은 것은 사실이다. 격차 >= 1.0은 상당 부분 진짜다.

하네스: `src/lib/storeEval/_ownFacilityGap.test.ts` (로컬 전용, 기각 기록)

## ③ 관리 — QSC로 채우면 안 된다

사용자 제안: *"FC다움에 QSC 점검표로 볼 수 있긴 해. 주관적 데이터로."*
(인테리어 노후도는 QSC에 없다 — *"청결관리니까"*.)

그리고 사용자 본인이 기각했다:

> *"신규매장에 판단하는 지표로 쓸 건데 신규매장이 어케 관리할지 모르니까. 가맹점 평균값으로
> 하는 게 어떤데. 지금 가맹점 매출 평균값을 기본으로 하니까 어찌 됐든 관리 부분도 평균값에
> 수렴하는 거 아닌가."*

맞다. 이 저장소가 세 번 겪은 실패와 같은 구조다 — **분모(또는 입력)는 예측 시점에 알 수 있어야 한다.**

```
지금:   자사 관리 = 4.00 (평균)     -> 신규 후보지도 4.00을 넣으면 된다
바꾸면: 자사 관리 = 매장마다 다름   -> 신규 후보지의 관리 점수를 "예측"해야 한다
```

그 예측 오차가 매출 예측 오차에 곱해진다. 그리고 학습이 실매출로 되어 있으므로
**평균 관리 수준은 이미 계수에 녹아 있다.**

→ **예측식에 넣지 않는다.** 다만 **오차 진단용으로는 가치가 있다** — 오차 20%를 넘는
매장이 QSC 점수가 낮다면 "모델이 틀린 게 아니라 그 매장 운영이 평균 이하였다"를 가릴 수 있다.

## ④ N011 마산산호점 — 외삽이지만 안전하다

후보지 9곳 중 N011만 경쟁력격차가 학습 범위 밖이다.

```
학습 범위(기존 38곳)  1.000 ~ 1.810
N011                  1.951   (최대보다 7.8% 위)
나머지 8곳            1.286 ~ 1.669   범위 안
```

자료는 멀쩡하다. 경쟁점 2곳 모두 `surveyLevel=상세` / `investigationStatus=조사완료` /
2026-09-01 방문이고, 둘 다 `interiorScore=1`이라 점수가 낮은 게 실제 상태다.
학습군에도 비슷하게 약한 상권이 있다(시흥은계점 경쟁점평균 1.978 vs N011 1.988).

격차 구간별로 모델이 실제로 맞았는지 보면 **높은 쪽이 오히려 더 정확하다.**

| 격차 구간 | 곳수 | 평균 오차 |
|---|---:|---:|
| **1.7 이상** | 3곳 | **5.59%** |
| 1.5~1.7 | 11곳 | 9.82% |
| 1.3~1.5 | 18곳 | 10.66% |
| 1.3 미만 | 6곳 | 8.44% |

강릉교동점(격차 1.810) 오차 0.4%, 시흥배곧점(1.781) 3.1%.

→ **N011 예상매출 8,673만원을 의심할 근거가 없다.**

하네스: `src/lib/storeEval/_n011Extrapolation.test.ts` (로컬 전용)

## 오늘 실제로 얻은 것

### 열위 표본은 자사 매장에서 영원히 안 나온다

```
우리는 항상 새 매장을 연다.
새 매장은 기존 경쟁점보다 시설이 좋다.
-> "우리가 밀리는 사례"는 구조적으로 생기지 않는다.
```

**이건 표본을 45곳·60곳으로 늘려도 안 풀린다.** 매장 수의 문제가 아니라 사업 구조다.

메모리 `project_sample_gate`("표본 45~50곳까지 산식 개선 동결")는 이 부분에 한해
효력이 없다 — 기다려도 이 축은 안 열린다.

### 그래서 경쟁점끼리 짝 비교가 우회로가 아니라 정공법이다

`share-elasticity-pair-test-2026-09-15.md`의 27짝(열위 13 / 우위 14)이 열위를 학습할
**유일한 경로**다. 어제는 "총수요를 못 만들어서 어쩔 수 없이 쓰는 우회로"로 적었는데,
그 평가를 정정한다.

### 기존점과 후보지는 같은 기준이다 (혼동 정리)

| 축 | 상태 |
|---|---|
| 기존점 vs 후보지 | **같은 기준.** 기존점이 기준이고, 어긋나 있던 후보지 9곳을 2026-09-15에 맞췄다 |
| 자사 vs 경쟁점 | **다른 기준.** 맞추면 악화되므로(위 ①) 의도적으로 그대로 둔다 |

기존 가맹점을 "검토했는데 적용 안 한" 것이 아니라, **검토했더니 고칠 것이 없었다**
(`location-eval-roadview-review-2026-09-15.md` §1).
