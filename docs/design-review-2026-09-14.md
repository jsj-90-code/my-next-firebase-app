# 디자인·UI 평가와 개선 방향 (2026-09-14)

사용자 요청: "배치도 작업툴·메인홈·점포평가에 추가할 요소나 기능, 그 외 퀄리티 높이는 작업이나
디자인 UI 요소 등 개선 방향을 잡아보자. 지금 웹이 디자인 전문가적인지도 평가해보고."

**평가는 눈으로만 하지 않았다** — 운영 배포본을 실제로 열어 화면을 찍고, 색은 `dataviz` skill의
검증기(`validate_palette.js`)로 계산했다.

---

## 1. 총평 — "사내 도구로는 상위권, 제품이라기엔 미달"

### 잘돼 있는 것 (빈말 아님)

- **디자인 토큰 체계가 실재한다.** `--sl-ink` / `--sl-gold` / `--sl-ok|warn|danger|info` /
  `--sl-step-a|b|c`를 라이트·다크 각각 정의하고, 화면은 하드코딩 대신 토큰을 쓴다. 사내 도구에서
  이 정도 하는 경우는 드물다.
- **대비를 실제로 측정한 흔적이 코드에 있다.** `globals.css`에 "`--sl-gold`는 라이트 배경에서
  3.92:1로 본문 기준에 못 미친다(2026-09-11 측정)"는 주석이 있다. 감으로 안 골랐다는 뜻이다.
- **다크모드가 자동 반전이 아니라 별도 설계**다. 토큰을 따로 정의했다.
- **히어로 숫자 위계가 좋다.** 결과 탭의 "약 5,800만원"(검정 카드) + 아래 작은 원 단위 병기는
  교과서적으로 맞다.
- **좁은 화면 대응이 실측으로 검증돼 있다**(2026-09-13, 390px·320px 표 14개).
- **경고·상태 배지 체계**(주의/정보/완료)가 일관된다.

### 측정으로 드러난 결함 — 감상이 아니라 숫자다

`dataviz` 검증기를 "왜 이 매출인가" 기여도 막대의 실제 색에 돌렸다.

| 대상 | 색 | 정상시각 구분도 | 색각이상 | 판정 |
|---|---|---:|---:|---|
| 기여도 막대 (라이트) | `#7F5B17` / `#426B46` | **ΔE 9.6** | 5.4 | **FAIL** |
| 기여도 막대 (다크) | `#E0B25A` / `#8FC492` | **ΔE 11.5** | 6.6 | **FAIL** |
| 단계 색 3종 (라이트) | `#7a4fa0`/`#9a5f19`/`#1e796e` | ΔE 16.9 | 10.6 | **PASS** |

기준은 정상시각 ΔE 15다. **기여도 막대의 두 색은 색각이상이 없는 사람도 구분하기 어렵다.**
게다가 이 화면에는 "인쇄 / PDF 저장" 버튼이 있다 — 흑백 인쇄되면 더 붙는다.

> 완화 요인: 막대가 0축 기준 좌/우로 갈리고 `+4.7%` / `-18.2%` 직접 라벨이 붙어 있어, **부호는
> 색 없이도 읽힌다.** 그래서 "못 읽는다"가 아니라 "색이 정보를 더해주지 못한다"가 정확하다.
> 다만 `dataviz` 기준으로 정상시각 ΔE 15 미달은 직접 라벨로 면제되지 않는 항목이다.

**반대로 단계 색 3종은 통과다** — 계산법 화면의 1·2·3 배지는 잘 골랐다.

### 구조적 결함 3가지

**① 숫자 도구인데 시각화가 거의 없다.** 결과 탭에서 이런 문장을 읽게 한다.

> 실제로 영업 중인 38곳의 매출과 나란히 놓으면 이 예상값은 38곳 중 25번째 수준입니다
> (기존점 중앙값 6,400만원). PC 1대당으로 보면 58.3만원으로, 기존점 대당 중앙값
> 60.7만원보다 낮습니다 (38곳 중 23번째).

**이건 점 하나짜리 분포 그림이면 0.5초에 읽힌다.** 지금은 4줄을 읽고 머릿속에서 그려야 한다.

**② 한 화면 안에서 단위 규칙이 흔들린다.** 히어로는 "약 5,800만원"인데, 같은 화면 아래에
"PC 26,918,233원 + 상품(먹거리) 31,362,217원"이 원 단위로 있다. 2026-09-13에 통일했다고
기록돼 있는데 이 줄은 남았다.

**③ 서로 다른 축이 한 열에 섞여 있다.** (⚠️ 아래 "고친 결과" 참고 — 화면 버그가 아니라 원본 설계였다.)
대시보드 "최종운영판정" 열에 `평가 완료`(진행 상태)와
`포화 주의`(진단 결과)가 같은 자리에 뜬다. 둘은 다른 축이라 정렬·필터가 성립하지 않는다.

## 2. 화면별 개선 방향

### 메인홈

| | 지금 | 제안 |

## 4. 우선순위 — 판단을 그르칠 수 있는 것부터

**P0 — 잘못 읽힐 수 있다**

1. **기여도 막대 색 교체** (측정 근거 있음, 인쇄까지 함)
2. **단위 혼용 정리** — 한 화면에 만원/원이 섞여 있다
3. **대시보드 판정 열 분리** — 진행 상태와 진단 결과

**P1 — 같은 일을 더 빨리**

4. 기존점 분포를 **문장 → 그림**으로
5. 대시보드 **정렬·순위·필터 연결**
6. 배치도 **상시 경고 정리 + 존 묶기**
7. 배치도 **빈 캔버스에 업로드 버튼**

**P2 — 완성도**

8. 메인홈 여백·최근 작업
9. primary 버튼 색 통일(검정 → 테라코타)
10. 결과 탭 결론을 맨 위로

## 5. 이 문서의 한계

- **사용자 인터뷰를 하지 않았다.** "무엇이 불편한가"는 안 물어봤고, 화면과 코드만 봤다.
  실제 쓰는 사람이 다르게 느낄 수 있다.
- ~~성능은 안 쟀다~~ → **쟀다(§7). 문제 없다.**
- **색 검증기는 categorical 팔레트 기준**이다. 발산형(diverging) 쌍에 그대로 들이댄 것이라
  엄밀히는 범위를 벗어난다 — 다만 "두 색이 서로 구분되는가"라는 질문 자체는 유효하다.

## 7. 추정으로 미뤄뒀던 것을 실제로 쟀다 (2026-09-14)

### 성능 — 손댈 게 없다

| 화면 | DOM 완료 | CLS | 긴 작업 | JS 전송 | 요청 |
|---|---:|---:|---:|---:|---:|
| 대시보드 | 1,144ms | 0.0043 | — | 497KB | 100 |
| **결과 탭**(가장 무거움) | **827ms** | **0.0043** | **0건** | 807KB | 123 |

CLS 기준은 0.1인데 0.004고, **메인 스레드를 막는 긴 작업이 하나도 없다.** 콘솔 오류도 0건이다
(측정 중 뜬 경고 1건은 내 측정 코드가 쓴 deprecated API였다). 결과 탭 요청 123건 중 53건이
Firestore인데 이미 읽기 예산으로 측정·기록된 패턴이다(결과 탭 799건).

**JS 807KB가 유일하게 큰 숫자지만 체감을 해치지 않으므로 최적화할 이유가 없다.**

### 접근성 — 걱정보다 훨씬 나았다

| 항목 | 결과 탭 | 대시보드 |
|---|---:|---:|
| 라벨 없는 입력 | 0 | 0 |
| 이름 없는 버튼·링크 | 0 / 32 | 0 / 42 |
| alt 없는 이미지 | 0 | 0 |
| 제목 단계 건너뜀 | 0 | 0 |
| `lang` | ko | ko |
| **scope 없는 `th`** | — | **9 / 9** |

딱 하나 남은 게 표 헤더의 `scope`였다(전체 115개 중 12개만 있었다). 85개를 채워
**이제 `<th>` 97개 전부에 `scope="col"`이 있다.** 나머지 항목은 애초에 문제가 없었다 —
"실익이 낮다"고 미뤄뒀던 판단은 맞았지만, 이유는 **이미 잘돼 있어서**였다.

### React 코드 품질 — 리팩터링하지 않기로

`ResultTab.tsx`가 1,461줄이라 분리를 검토했다. `vercel:react-best-practices`의 위험 패턴을
실제로 찾아봤다.

| 검사 | 결과 |
|---|---|
| `{숫자 && ...}` (0이 화면에 찍히는 버그) | **0건** |
| 컴포넌트 안에서 컴포넌트 정의 | **0건** |
| `react-hooks` 린트 | **에러 0** |
| 긴 작업 | **0건**(위 성능 측정) |

**그래서 분리하지 않는다.** 이 파일은 길지만 이름 붙은 하위 컴포넌트 10개로 나뉘어 있고 각각
40~150줄이다. 줄 수는 문제의 증거가 아니다 — 실제 문제를 찾아봤는데 없었다. 가장 중요한 화면을
이유 없이 건드리는 위험만 남는다.
