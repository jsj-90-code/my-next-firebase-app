# 견적서 단가 갱신 (블랙·골드)

2026-10-23 집 PC에서 처음 만들었다. **신규 가맹점 본계약 견적서**다 — 영업부가 계약에 그대로 쓰니 틀리면 계약 금액이 틀린다(사용자: "실수하면 큰일"). 아래 순서를 건너뛰지 않는다.
- **사용자가 미리보기 표를 보고 "적용해"라고 하기 전에는 `apply`·`sync`를 실행하지 않는다.** "그대로 해", "응"도 미리보기를 본 뒤의 답일 때만 승인으로 본다.
- 숫자는 스크립트 출력에서만 옮긴다. 암산·추정한 금액을 보고에 쓰지 않는다.
배경·결정 이유: 업무위키 `LLM위키/2_위키/가맹 운영/가맹 계약 견적서.md` 1-1절.

## 시트 구조 (알고 시작할 것)

- 시트 4개: 블랙·골드 각각 **원본**(원가·마진 있음, 사용자만)과 **영업부용**(원가 없음, 잠김). 주소는 `scripts/quote/lib.mjs`의 `BOOKS`.
- **원본만 고친다.** 영업부용은 `sync.mjs`로만 바꾼다(원가가 영업부 시트에 한 순간도 안 들어가게 원본 안에서 지우고 보낸다).
- 원가는 **부가세 별도**. PC 탭 N열 "부품별 원가", 서버 탭 K열(+ O열 "매입가 VAT 포함"). 판매 단가 F열도 부가세 별도.
- 같은 부품이 여러 줄에 있다(예: RTX5060 8GB = 카운터 세트 N10 + 좌석 N18). 블랙·골드는 부품·원가가 같고 **판매 단가는 다르다**(좌석 기본 블랙 105만·골드 79만) — 단가는 등급별로 따로 정한다.
- 원가 칸이 수식이면(32GB = `=N16*2`, 지원금 품목 = 차액 수식) 안 고친다. 따라 바뀐다.
- 평소 갱신은 **PC 및 주변 기기 탭만**. 서버·가구·인테리어는 변동이 드물어 사용자가 말할 때만(`--tabs all`).

## 1. 단가표 받기

사용자는 **항목 + 모델명 + 가격(부가세 포함)**으로 준다(10-23 사용자: "모델명으로 줄게, 그래야 정확하지. 항목과 모델명 둘 다"). 받은 그대로 JSON으로 적는다(스크래치패드에):

```json
[{ "항목": "그래픽카드", "모델": "RTX5060 8GB", "가격": 565000 },
 { "항목": "메모리", "모델": "DDR5 16GB", "가격": 295000 }]
```

- 가격이 "56만 5천"처럼 오면 숫자로. **부가세 별도라고 하면** ×1.1 해서 넣고 그렇게 했다고 말한다(기본은 포함가).
- 모델명이 시트 표기와 다를 수 있다(공백·대소문자는 무시함). 못 찾으면 2단계에서 "못 찾음"으로 나온다 — 시트의 비슷한 줄을 보여 주고 물어본다. 추측해서 고르지 않는다.

## 2. 미리보기 (시트는 그대로)

```
node scripts/quote/price.mjs preview <단가표.json>
```

- 블랙·골드 원본에서 줄을 찾아 원가 전→후, 판매 줄별 단위당 마진 전→후(%)를 보여 준다. 원본 안 임시 탭에서 실제로 계산하고 지운다(세트 원가 합계 같은 수식까지 정확).
  여러 줄 원가를 한 칸에 묶은 합계(PC 탭 L16:L34 = 좌석 세트 전체)는 단위당 원가로 쓰지 않는다 — 10-26 전엔 메모리 줄이 "원가 150만·⚠ 손해"로 잘못 나왔음.
- 100대·80평 기준 총 마진 계산 때문에 책마다 1~2분 더 걸린다.
- 계획은 `~/.isens-quote/last-plan.json`에 저장된다.
- 사용자에게 **대화창에 표로** 보여 준다: 원가가 바뀌는 줄, "(같음)"인 줄은 한 줄로 묶어서, 마진이 마이너스(⚠ 손해)인 줄은 맨 위에.
  웹 페이지·파일로 띄우지 않는다(10-23 사용자: "채팅으로만 하자" — 페이지에서 골라도 결국 대화창에 다시 쳐야 해서 두 번 일).
- **표의 줄마다 견적서(블랙/골드)·탭 이름·칸(예: N16)·시트의 품목 글자를 그대로 적는다**(10-23 사용자: 비슷한 항목이 다른 탭에 있을 수 있음).
  탭 이름을 줄여 쓰지 말고, 같은 모델이 두 탭 이상에서 잡히면 그 사실을 표 위에 한 줄로 따로 알린다.
- **확인받을 것**: 묶음 표시(×N)가 붙은 줄, 사용자가 말한 것과 다른 제품으로 보이는 줄. 빼야 하면 `--skip "탭:행,..."`로 다시 미리보기.

## 3. 판매 단가 정하기

원가가 바뀐 판매 줄마다 선택지 세 개와 **관리선 규칙에 따른 추천**을 보여 주고 **사용자가 고르게** 한다.

**관리선 규칙(2026-10-26 사용자 확정)** — 100대·80평 기준 계약 1건 총 마진의 관리선 **블랙 8,000만 · 골드 5,000만**(부장님 목표보다 위, 현재 업견적 마진 근처):
- 원가가 올라도 **판매 단가 그대로 둔 총 마진이 관리선 이상이면 → 전부 '그대로'**(그 품목 마진은 줄어도 됨).
- 관리선 **미만이면 → 원가가 오른 줄을 '마진금액 유지'**로 추천. 추천대로 해도 모자라면 미리보기에 "추천대로 해도 모자람"이 나온다 — 어디를 더 올릴지 사용자에게 묻는다.
- 원가가 내리면 단가 그대로(마진이 늚). 새 품목은 비슷한 기존 품목 마진율로 단가 초안 → 넣은 뒤 총 마진이 관리선 이상인지 확인.
- 관리선은 부장님 목표 아래로 내리지 않는다. 값은 `price.mjs`의 `FLOOR`. 블랙은 여유가 작다(10-26 +598만 ≈ 대당 6만) — 인상 추천이 너무 잦으면 7,500만으로 낮출지 사용자에게 묻는다.
- 미리보기가 추천 단가를 `~/.isens-quote/recommended-prices.json`에 저장한다 → 사용자가 "추천대로"면 `apply --prices` 그 파일.
  사용자가 다르게 고르면 그 단가로 JSON을 만들어 **`price.mjs check --prices <파일>`로 총 마진·관리선·지원금을 먼저 보여 준 뒤** 승인받고 apply.

**판단 기준은 계약 1건 총 마진이다**(10-23 사용자, 인계 때 들은 개념): '그대로'로 둘지는 위 관리선과 견줘 정한다 — 아래 목표는 관리선보다 낮은 바닥값이라 판단 기준이 아니다.
미리보기의 "계약 1건 총 마진(100대·80평 기준) 전→후 | 목표 대비" 줄을 표 맨 위에 보인다.
목표(2026-10-26 부장님 확인, 사용자 전달):
- 계약 1건 목표 마진 **블랙 7,000만 원 · 골드 4,000만~5,000만 원**, **100대 매장 기준**(평수는 80평으로 봄 — 10-26 사용자). 값은 `price.mjs`의 `TARGET`·`STD`.
- 지금 견적은 업견적(단가를 높게 잡아 둠)이라 목표보다 높게 나온다 — 목표를 넘는다고 단가를 내리자는 뜻이 아니다.
- 선투자: 1억 중 7,500만 원(대수 100 넘으면 더)은 10개월 분할로 돌려받고, **성실이행 지원 2,500만 원은 기본적으로 못 받는 돈**(이슈 시 회수).
  그래서 블랙 원본 '본사 내부 정리'에 "보정 ④ 선투자 성실이행 지원 = −F18"을 넣어 본사 마진에서 뺀다(10-26). 골드는 선투자 없음.
- 100대 기준 값은 원본 안 숨김 임시 탭(`__마진100_…`)에 품목·최종 탭을 복사해 대수 100·평수 80만 바꿔 계산한다(원본 탭은 그대로, 끝나면 지움).
  예시 매장(블랙 110대) 기준 값은 "(참고)" 줄 — 목표와 견주지 않는다.
- **인터넷 지원금 품목 합계(PC 탭 I35)는 800만 이하**여야 한다(프로모션 고정 금액, 10-26 사용자). I35는 품목 단가×수량의 **그냥 합계**(10-29 사용자: 절삭하면 단가 수정 때 헷갈림 — 10-26 `ROUNDDOWN(…,-5)`에서 바꿈). 10-29부터 품목은 품의 전 5종(35~39행).
  넘으면 최종 탭이 아니라 **단가 수정이나 제품 교체**로 맞춘다 — 미리보기에 ⚠ 줄이 나오고, `apply`는 판매 단가로 800만을 넘기면 아무것도 안 쓰고 멈춘다(종료 코드 4).
  원본 '본사 내부 정리' 맨 아래 줄에도 같은 확인(정상/⚠)이 있다 — 시트를 직접 고칠 때용.

| 선택지 | 뜻 |
|---|---|
| 그대로 | 판매 단가 유지, 마진이 줄거나 늚 |
| 마진금액 유지 | 원가 오른 만큼 단가도 올림(10만 원 이상은 만 원, 아래는 천 원 단위 반올림) |
| 마진율 유지 | 원가 비율대로 단가 조정(같은 반올림) |

- 단가가 수식인 줄(`=F16*2`, 서버 `=ROUND(K*1.1,-2)`)은 "자동"이라 묻지 않는다.
- 블랙·골드 단가가 다르면 각각 묻는다. 사용자가 "다 그대로"라고 하면 단가 파일 없이 간다.
- 고른 단가는 JSON으로: `[{ "book": "black", "tab": "PC 및 주변 기기 내역", "row": 16, "price": 330000 }]`
- 사용자가 자주 같은 쪽을 고르면(예: 메모리는 늘 마진금액 유지) 다음부터 "지난번처럼 ○○로 할까요?"로 묻고, 사용자가 규칙으로 하자면 이 절에 적는다.

## 4. 원본에 쓰기 → 영업부용 반영 → 검증

```
node scripts/quote/sync.mjs black --check     ← 먼저: 영업부용 직접 수정 확인(시트 안 바꿈)
node scripts/quote/sync.mjs gold --check
node scripts/quote/price.mjs check --prices <단가.json>     ← 사용자가 추천과 다르게 골랐을 때: 총 마진·관리선 먼저(시트 안 바꿈)
node scripts/quote/price.mjs apply [--prices <단가.json>]   ← 추천대로면 ~/.isens-quote/recommended-prices.json
node scripts/quote/sync.mjs black
node scripts/quote/sync.mjs gold
```

- 판매 단가를 하나도 안 바꾸는 갱신이면 `--check`·`sync`는 `apply` 뒤 "영업부용 반영: 필요"일 때만(아래 참조).
- **원본에 쓰기 전에 `--check`부터** 돌린다(10-23 사용자: "원본은 두고 영업부용만 고친 경우" — 그 수정이 반영 때 날아가면 일이 난다).
  "직접 바뀐 칸"이 하나라도 나오면 `apply`로 가지 않고 목록(견적서·탭·칸·전→후)을 표로 보여 준 뒤 **사용자에게 고르게** 한다(기본값 없음):
  - **원본에 옮기기**(추천 — 맞는 수정일 때): `sync.mjs <책> --adopt` → 원본 같은 칸에 옮기고 다시 읽어 확인한 뒤 반영. 그다음 단가 갱신이면 2단계(미리보기)부터 다시.
  - **영업부용 수정 버리기**(틀린 수정일 때): `sync.mjs <책> --force`. 버려지는 값을 한 번 더 보여 주고 "버려도 되나요?"를 확인받는다.
  - `--adopt`가 "옮기지 못한 칸"으로 멈추면(원본도 그 사이 바뀜 / 원본이 원가 계산 수식 칸) 아무것도 안 옮긴 상태다 — 칸마다 원본 값·영업부용 값을 나란히 보여 주고 어느 쪽인지 묻는다. 원가 수식 칸은 판매 단가를 원가에서 계산하는 칸이라, 영업부용 값을 원하면 원가(K열)를 바꿔야 하는지부터 묻는다.
  - 값·수식만 비교한다(서식 변경은 못 잡음). 기준 기록은 블랙·골드 모두 2026-10-23 첫 반영부터.
  - **'정보입력(댓수,평수)' 탭 대수·평수(B3·B4)**는 실무자가 상담하며 바꾸는 칸이라 원본과 안 맞아도 된다(2026-10-30 사용자).
    `sync`는 이 두 칸을 직접 수정으로 잡지 않고, 덮어쓰지 않으며, 검증은 영업부용 대수·평수로 다시 계산한 원본 사본(숨김 `__검증_…`)과 대조한다. 값은 `lib.mjs`의 `SALES_INPUTS`.

- **영업부용 반영이 필요한지는 `apply` 출력의 "영업부용 반영:" 줄로 정한다**(10-30 사용자: "공급가만 수정되는 거면 영업부용은 수정할 필요 없을 듯").
  PC 탭 원가만 바뀌고 판매 단가가 그대로면 영업부용에 보이는 칸(J열까지)이 안 바뀌어 "필요 없음" → 그 책은 `sync`를 돌리지 않는다(`--check`도 생략).
  서버 탭 원가는 판매가가 원가 수식(`=ROUND(K*1.1,-2)`)이라 원가만 바꿔도 "필요"로 나온다 → 그때만 `--check` → `sync`.

- `apply`는 미리보기 뒤 원본 원가·판매 단가 칸이 바뀌었으면 **아무것도 안 쓰고** 멈춘다 → 2단계부터 다시.
- `apply`는 쓰기 전에 임시 탭에 같은 값을 넣어 **정답지**를 만들고, 쓴 뒤 ① 바뀐 입력 칸 = 계획한 칸·값 ② 원본 탭 전체 값 = 정답지를 대조한다.
  어긋나면 그 회차에 쓴 칸을 전부 원래 값으로 되돌리고(되돌아온 것까지 확인) 멈춘다 — 이때는 `sync`를 돌리지 말고 출력을 사용자에게 그대로 보인다.
  성공 줄의 "적용 확인: 바뀐 칸 = 계획 N칸, 정답지와 전체 일치 ✓"가 없으면 성공으로 보고하지 않는다(10-23 사용자: "표는 맞게 줬는데 실제 반영이 어긋나는 경우"를 막을 것).
- `sync`는 영업부용에서 누가 직접 고친 칸이 있으면 반영하지 않고 목록을 보여 준다 → 사용자에게 보여 주고, 원본에 옮길지 덮어쓸지(`--force`) 묻는다.
- `sync`가 검증 차이로 멈추면 백업이 남는다 → 차이를 보여 주고 `--rollback`(되돌림) / `--accept`(확정)를 묻는다.
  `--accept`는 검증을 다시 돌려 차이가 있으면 확정하지 않는다 — 사용자가 그 차이를 보고도 확정하겠다고 할 때만 `--accept --force`.
  `--rollback`은 반영 직전 기록(원본 숨김 탭 `__반영직전기록`)과 칸마다 대조한다. "되돌림 확인 실패"나 "기록이 없어 대조하지 못함"이면 백업이 남은 상태 — 성공으로 보고하지 말고 출력을 그대로 보인다.
- `sync`는 영업부용 탭을 그대로 두고 바뀐 칸만 덮어쓴다(10-24부터, 수정 기록·댓글·탭 링크 유지). **시트 위에 띄운 그림·도형은 따라가지 않고 검증도 못 잡는다**(구글 API가 못 읽음, 10-24 기준 블랙·골드 원본에 없음).
  원본에 그림을 넣거나 바꿨다는 말이 나오면 영업부용에도 손으로 맞춰야 한다고 사용자에게 알린다.
- 시트 수정은 사용자 본인 구글 계정으로 된다(로그인: `node scripts/quote/login.mjs`, PC마다 한 번). "로그인 정보 없음 → 서비스 계정" 경고가 뜨면 사용자에게 알리고 로그인부터 하게 한다(수정 기록에 로봇 이름이 남는 걸 싫어함).
- 구글 한도(429) 재시도 메시지는 정상 — 기다리면 끝난다.

## 5. 보고

짧게, 숫자 위주로:
- 블랙·골드 각각: 고친 원가 칸 수, 바뀐 판매 단가(전→후), **예시 매장 최종 금액 전→후**(`apply` 출력)
- 마진이 마이너스인 줄이 남았으면 따로 한 줄
- 검증 결과(전체 일치 / 차이)

## 하지 말 것

- 영업부용 시트를 직접 고치지 않는다(반영 기록과 어긋나 다음 반영 때 "직접 수정"으로 잡힌다).
- 시트 서식·행 높이·병합을 원본에서 바꾸지 않는다 — 단가 갱신 범위 밖. 사용자가 서식을 말하면 그때 따로.
- 잠금(보호)을 새로 걸거나 풀지 않는다 — `sync`가 반영 전 상태를 그대로 유지한다(10-23 사용자: "원래 안 걸린 거 걸지 마").
- 원가·마진 숫자를 영업부용이나 밖으로 나가는 글에 쓰지 않는다.
